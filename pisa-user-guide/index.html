    User Guide¶

    How to set up a project with Pisa and generate working code from specs (domain model, form description etc.).

    Maintenance: This guide describes pisa 0.13.0 (released as v0.13.0; with enum, @table, @column, .adl, propose-architecture, propose-model, the second target hono-prisma (TypeScript), runtime in the .adl, @operations, login with users and roles (authentication session, pisa hash-password), roles in the .adl, the display mode of the pages, pisa play, pisa update-versions and the pipeline and scm blocks of the .adl). It is updated with every change to commands, options, spec formats or generated behavior. If something is wrong: pisa --help is the source, this guide follows it.

    To try it out: mkdir my-project && cd my-project && pisa init creates doc/ (this guide and both tutorials) and spec/; pisa play lists the tutorials, pisa play <name> plays one (pisa play). The Spring Java tutorial leads from a prose description to a running Java application in an hour (with the LLM proposals); the Hono TypeScript tutorial builds the same application as a TypeScript project with Hono and Prisma.

    Installing Pisa¶

    Pisa is a single, precompiled program (no Bun, no Node, no dependencies). It is a file in the releases of the public repository Arcware-io/pisa; downloading needs no login and no GitHub CLI.

    System File
    macOS, Apple Silicon (M1 and newer) pisa-darwin-arm64
    macOS, Intel pisa-darwin-x64
    Linux, x86-64 pisa-linux-x64
    Linux, ARM pisa-linux-arm64
    Windows, x86-64 pisa-windows-x64.exe
    Windows, ARM pisa-windows-arm64.exe

    Which architecture you have is shown by uname -m (macOS/Linux: arm64/aarch64 = ARM, x86_64 = x64) or, on Windows, Settings → System → About → System type.

    Three ways; the scripts and the formula are in the repository Arcware-io/pisa. This guide is also available as a website: https://arcware-io.github.io/pisa/. Not tried by the author: install.sh, install.ps1 and the Brew formula (they were read, not run).

    With a script (macOS, Linux)¶

    curl -fsSL https://raw.githubusercontent.com/Arcware-io/pisa/main/install.sh | sh

    install.sh detects system and CPU, downloads the matching file from the latest release, makes it executable, removes the quarantine on macOS, shows pisa --version and points out if the folder is not in the PATH. Default folder: ~/.local/bin. Options --version vX.Y.Z and --dir <folder>:

    curl -fsSL https://raw.githubusercontent.com/Arcware-io/pisa/main/install.sh | sh -s -- --version v0.13.0 --dir ~/.bin

    Windows (PowerShell)¶

    irm https://raw.githubusercontent.com/Arcware-io/pisa/main/install.ps1 -OutFile install.ps1; .\install.ps1

    install.ps1 picks x64 or arm64, puts pisa.exe into $HOME\bin (option -Dir), removes the "from the internet" mark and adds the folder to the user PATH (open a new terminal); -Version vX.Y.Z picks a release. Scripts blocked? powershell -ExecutionPolicy Bypass -File .\install.ps1. Not tried on a real Windows.

    Homebrew (macOS, Linux)¶

    brew tap Arcware-io/pisa https://github.com/Arcware-io/pisa
brew install pisa

    The formula (Formula/pisa.rb in the repository Arcware-io/pisa) downloads the same file from the release and checks its checksum. There is no tap name of its own (homebrew-…): hence the address in the first command.

    By hand¶

    Download the file from the table from the release page (in the browser, or with curl as below), make it executable and put it into a folder in the PATH.

    # macOS (Intel: pisa-darwin-x64) and Linux (pisa-linux-x64, pisa-linux-arm64)
curl -fSL -o pisa https://github.com/Arcware-io/pisa/releases/latest/download/pisa-darwin-arm64
chmod +x pisa
mkdir -p ~/.bin && mv pisa ~/.bin/pisa        # ~/.bin must be in the PATH (e.g. in ~/.zshrc)
xattr -d com.apple.quarantine ~/.bin/pisa     # macOS only, only if you downloaded the file in the browser
pisa --version

    # Windows
Invoke-WebRequest https://github.com/Arcware-io/pisa/releases/latest/download/pisa-windows-x64.exe -OutFile pisa.exe
mkdir $HOME\bin -Force; Move-Item pisa.exe $HOME\bin\pisa.exe
setx PATH "$env:PATH;$HOME\bin"        # takes effect in a new terminal only
pisa --version

    If macOS says "cannot be opened" at start, it is Gatekeeper's quarantine: the xattr command above fixes it. At the first start Windows SmartScreen may warn ("More info → Run anyway"). build-all.sh and release.sh are Bash scripts (Git Bash or WSL), on Windows you use the finished release files. Starting Pisa by hand on Linux and Windows has not been tried.

    Updating and source code¶

    New version: download the same file again and replace it (or run the script again). pisa --version shows what is running.

    Setting up editor and PlantUML¶

    Two things make working with the specs pleasant, both optional:

    1. Pisa plugin "Pisa Languages (DML, ADL)" for .dml (and .adl, the architecture language): syntax colors, errors while typing, and when you save a .dml it writes the class diagram of the model (domain-model.puml and domain-model.md next to the .dml). The plugins can also format .dml and .adl (VS Code: "Format Document"; IntelliJ: Reformat Code, if LSP4IJ formatting is active, not checked). Style: 4 spaces, { at the end of the line, one field per line, name: Type, one blank line between entities. A file with a syntax error is not changed.
    2. PlantUML, so that the diagram and the Salt mockups in .ui.md appear as pictures.

    Pisa plugin for IntelliJ¶

    Requirements: IntelliJ IDEA 2024.3 or newer (build 243) and Node.js (the language server runs with node). The plugin looks for node in the PATH of your shell, with nvm and in the usual Homebrew folders; on macOS an IDE started from the Dock sometimes finds none. Then set the environment variable DML_NODE to the executable (e.g. export DML_NODE=$(which node) and start the IDE from the terminal).

    Windows: The plugin only looks for node, not node.exe, and does not know nvm-windows. It therefore does not find Node there by itself: DML_NODE is required, set permanently, then restart the IDE:

    winget install OpenJS.NodeJS.LTS
setx DML_NODE "C:\Program Files\nodejs\node.exe"

    (Adjust the path for another installation, where node shows it.)

    1. Get dml-intellij-plugin-<version>.zip: from the GitHub release, or built yourself from source .
    2. Settings → Plugins → ⚙ → Install Plugin from Disk… and pick the zip. IntelliJ installs the dependency LSP4IJ from the Marketplace along with it (otherwise install it by hand).
    3. Restart the IDE. Open a .dml: colors and error messages appear, the server is called "Pisa Language Server (DML, ADL)" (the Language Servers window of LSP4IJ shows its state).

    The plugin contains the language server; a zip replaces an earlier version.

    Pisa extension for VS Code¶

    Requirement: VS Code 1.85 or newer. The language server is bundled in the extension and runs in VS Code's own Node, a separate Node installation is not needed.

    code --install-extension dml-vscode-extension-<version>.vsix

    or Extensions → ⋯ → Install from VSIX…. The .vsix comes from the GitHub release or from build-all.sh (which also installs it into your local VS Code). After that every .dml file opens with syntax colors and checking.

    PlantUML on the system¶

    Rendering diagrams and mockups needs PlantUML and Graphviz (dot) on the machine when a plugin uses the local way.

    # macOS (Homebrew)
brew install plantuml graphviz
# Debian/Ubuntu
sudo apt install plantuml graphviz

    # Windows (Chocolatey; with Scoop: scoop install plantuml graphviz)
choco install plantuml graphviz
# Java, if there is none yet
winget install EclipseAdoptium.Temurin.25.JDK

    On Windows dot.exe must be in the PATH (open a new terminal and check dot -V); otherwise set the environment variable GRAPHVIZ_DOT to C:\Program Files\Graphviz\bin\dot.exe. Check: plantuml -version and dot -V. PlantUML needs Java (JDK 17 or newer, which you have for Spring anyway). Pisa itself does not call PlantUML, it only writes the text.

    PlantUML in IntelliJ¶

    Install the plugin PlantUML integration (Settings → Plugins → Marketplace, search "PlantUML integration"; plugin ID plantuml4idea). It brings its own PlantUML; Settings → Languages & Frameworks → PlantUML allows your own plantuml.jar and the path to Graphviz (otherwise some diagrams are not drawn, Salt mockups need no Graphviz). After that IntelliJ shows .puml files in the preview window.

    For ```plantuml blocks in Markdown (domain-model.md, .ui.md) the Markdown preview should show the picture. This is the way of working Pisa assumes (the Salt preview section of the .ui.md is meant for it), but it is not checked in this guide for every IDE version. If only the source text appears, look for a PlantUML extension in Settings → Languages & Frameworks → Markdown.

    PlantUML in VS Code¶

    Install the extension PlantUML (jebbs.plantuml):

    code --install-extension jebbs.plantuml

    Alt+D (macOS: Option+D) shows the preview of a .puml or of a ```plantuml block. It renders locally with Java and Graphviz (see above, plantuml.render = Local, which is the default).

    The Markdown preview (Cmd+Shift+V, the diagrams in domain-model.md and .ui.md) is not rendered locally by the extension: it embeds pictures from a PlantUML server. If plantuml.server is empty, it says No PlantUML server, specify one with "plantuml.server", even if plantuml.render is Local and Java and Graphviz are installed (read in the source of extension 2.18.1: markdown-it-plantuml/render.js). Two ways:

    • Own server on the machine (the diagrams do not leave it; Docker needed, the command has not been tried here):
    docker run -d --name plantuml -p 8090:8080 plantuml/plantuml-server:jetty

    and in the settings (JSON) "plantuml.server": "http://localhost:8090". Port 8090, because 8080 is taken by the generated applications. - Public server: "plantuml.server": "https://www.plantuml.com/plantuml". Then the diagrams go onto the network: do not use it for confidential models.

    Not checked in this guide: the settings dialogs change between IDE versions. The menu names of your version are what counts.

    Quick intro: bootstrapping a project with specs¶

    Goal: in about ten minutes a running Spring Boot project with a REST API and a web UI for a domain model, without an LLM and without a network. (If you prefer to be guided: pisa init in a new folder, then pisa play and the tutorials in doc/, see above.)

    Requirements¶

    • pisa in the path (pisa --version shows e.g. pisa 0.3.0 (built …)), see Installing Pisa.
    • JDK 25 (the current LTS; with --java 17 and 21 work too) and Maven to start the generated project (Windows: choco install maven or Scoop). The commands in the guide are written for Bash; in PowerShell replace \ at the end of a line by `, cd and --out . work unchanged.
    • Recommended: the Pisa plugins (DML, ADL) and PlantUML for your editor (setup). Pisa works without them, but then .dml has neither checking nor diagram and the mockups stay text.
    • LLM access is needed only for the propose-… commands with an LLM (propose-model, propose-architecture, propose-layout; propose-specs needs none). This guide needs none: you write the model and draw the mockup yourself.

    1. Creating the project (init)¶

    pisa init --target spring-boot --out ./shop --group ch.example --artifact shop

    This creates a startable, empty Spring Boot project (pom.xml, application class, test, application.yml with H2 URL, user and console, GlobalExceptionHandler, README.md), the folder spec/ with a short English spec/README.md (which spec files there are, a short DML reference, a form and a use case example, "Next steps" and a pointer to the tooling: Pisa plugin, PlantUML) and the first spec of the project: project.spec.json. Also the folder doc/ with this user guide and both tutorials (so they are where the specs are written, and match the Pisa version that created the project; they are not part of the recipe; a pisa init without any arguments creates only doc/ and spec/, see pisa init). init never overwrites an existing (even edited) README.md or spec/README.md, not even with --force; files in doc/ stay until you pass --force. The main README names Pisa/DSDD first, then "Tooling" (JDK, Maven, Pisa) and "Next steps".

    {
  "target": "spring-boot",
  "groupId": "ch.example",
  "artifactId": "shop",
  "basePackage": "ch.example.shop",
  "javaVersion": "25",
  "database": "h2"
}

    project.spec.json records what kind of project it is (target technology and options). All following commands read it, you no longer need to pass --target.

    2. Writing the domain model (spec/*.dml)¶

    The model belongs in the project, in the folder spec/ (which init created, with a short spec/README.md explaining how to define domain model, forms and use cases; init points to it at the end). Create spec/shop.dml:

    entity Customer {
    @id id: Long
    name: String
    email: String? unique
    oneToMany purchases: Purchase mappedBy customer
}

entity Purchase {
    @id id: Long
    orderedAt: Date
    paid: Boolean
    manyToOne customer: Customer
}

    Short reference of the .dml language: Domain model. The files in spec/ together form one model (entities may refer to each other across files).

    3. Generating code (generate)¶

    cd shop
pisa generate --file spec/shop.dml --out .     # checks syntax and references, only then writes

    For each entity you get a JPA class, a Spring Data repository, a REST controller (/api/customers, /api/purchases, with paging) and an Alpine.js page (list, create, edit, delete). Also index.html (menu) and a class diagram of the model (spec/domain-model.md, .puml). The files under src/ are rewritten on every run — that is the generated part.

    4. Starting¶

    mvn spring-boot:run
    • UI: http://localhost:8080/
    • API: http://localhost:8080/api/customers
    • Database: H2 in memory (data is gone after a restart).

    4h. Restricting operations (@operations)¶

    The idea: By default you can do everything with every entity: create (create), read (read), change (update), delete (delete). If that should not hold for an entity, it is stated in the domain model, not in code. Without a statement everything is always allowed; Pisa never blocks anything by itself and the LLM proposals (propose-model, propose-specs) do not suggest it either.

    When @operations, when security.yml? @operations describes the entity: something that holds for everyone and belongs to the nature of the data (reference data, imports, log entries: never delete, never change). It is in the model because Pisa checks it against the use cases, and the application answers 405. What is allowed depending on the role ("clerks may only read companies") belongs in security.yml (4g); there the application answers 403. security.yml can never allow more than @operations allows.

    @operations(create, read, update)       // companies: no delete
entity Company {
    @id id: Long
    name: String unique
    oneToMany employees: Person mappedBy company
}

    The line goes after @table (if present) and before entity. Rules that the editor and generate check:

    • read must be included (lists and the selection fields of other entities need it; "write only" does not exist).
    • Allowed names: create, read, update, delete, none twice. They are not keywords: a field read or an enum value DELETE stays possible.
    • On a composed part (e.g. the Address of a Person) the statement is an error: it is edited together with its root, that is where it belongs.

    What happens in the application (the same in both targets, Spring and TypeScript):

    Place Without delete (example) Without create Without update
    REST interface DELETE /api/companies/<id> answers 405 with an Allow header POST answers 405 PUT answers 405
    Page of the entity no delete button no form for creating no edit button; the form appears only for creating (create) and for viewing (click on a row, without a save button, with "Edit" only where update is allowed)
    Table in the page of another entity – – "Open" leads only to the page, not into the form
    Generated tests test answers405ForADelete or answers 405 for a delete instead of the delete test the error cases when creating are dropped; test data comes directly from the repository test for 405 instead of the change test

    Repository and service stay complete: the block applies at the interface and in the pages, not in the code below. A disallowed operation always answers 405, even for ADMIN (see 4g): 405 means "the entity does not know this", 403 "you may not do this".

    Interplay with other specs:

    • Roles: the rights of a role in security.yml are intersected with @operations. If ADMIN has "*": [create, read, update, delete] and Company only @operations(create, read, update), even ADMIN may not delete a company. GET /api/me and the pages already show it intersected.
    • Use cases: a use case (.uc.md) with Test: löschen (delete) requires delete (ändern: update, anlegen: create; for a part the root counts). If it is missing, generate aborts and writes nothing: UC6 (spec/use-cases.uc.md): Company doesn't allow "delete" (@operations(create, read, update)) but the test line says "delete". Way out: allow the operation again, change the Test: line or drop the use case.
    • Pisa never deletes: if you drop a use case, its old browser test (test/ui/UC6.spec.ts or …/ui/UC6UiTest.java) stays and fails; delete it by hand. generate names it: Info: browser tests of use cases that are no longer in spec/*.uc.md - delete …, one file per line. If you lift a block, generate writes the tests and pages of the entity in full again.

    Back to "everything allowed": delete the @operations line (or name all four) and run generate. Example with steps and outputs: tutorial, step 7a (TypeScript: tutorial, step 7a).

    4g. Users, roles and login (authentication session)¶

    By default the application has no login, everything is open. With one line in the .adl it gets a login with users and roles, the same in both targets:

        container api : backend {
        authentication session     // without the line: no login
        …
    }

    Roles and their rights are in the .adl, in the block roles (it needs authentication session; the rights are not in the domain model):

        container api : backend {
        authentication session
        roles {
            ADMIN                      // a role without a block may do everything the entities allow
            USER {
                Company: read, update  // only these operations on this entity (create, read, update, delete)
            }                          // all other entities stay allowed; `*: read` sets it for "all others"
        }
        …
    }

    If the block is missing, the roles ADMIN and USER exist, both may do everything. The editor checks the block (a role only once, an entity only once per role, only the four operations; a name that the .dml in the same folder does not know is a warning) and jumps from the entity name to the entity (Go to Definition, in IntelliJ Ctrl+click; Find References lists the rules that name the same entity); whether the entities occur in the model is checked by generate (security.yml is not valid: … no entity …). propose-architecture writes the block from the description if it names roles and their rights ("User may read and change companies, but not create or delete them").

    init (again: init … --adl … --force) then writes the file security.yml into the project folder once (after that it is yours, Pisa never overwrites it; delete an existing security.yml first, so that it is created anew from the roles of the .adl), the login page login.html and the page change-password.html. Each role gets a development user: admin for ADMIN, user for USER, for every other role the role name in lower case (password user, to be changed at the first login).

    roles:                                   # what a role may do per entity ("*" = every entity)
  ADMIN:
    "*": [create, read, update, delete]
  USER:
    "*": [create, read, update, delete]
    "Company": [read, update]            # the list of an entity replaces "*"
users:
  - { name: admin, password: "$2b$10$…", roles: [ADMIN], mustChangePassword: true }
  - { name: user,  password: "$2b$10$…", roles: [USER],  mustChangePassword: true }
    • Rights: the union of a user's roles, intersected with @operations of the entity (a role can never do more than the entity allows). A new role or a new user needs no generate, only a restart of the application (it reads the file at start).
    • Display mode: a click on a row of the list opens the entry in the form, read-only (all fields locked, no save button, "Close" closes). Whoever may update additionally sees "Edit" there, which unlocks the form; the "Edit" button in the row edits directly as before. A role without update (or an entity with @operations without update) can therefore look at entries, also fields that are not columns in the list, but not change them. The behavior follows from the rights alone; today it cannot be set in the specs (only through your own page templates, see pisa eject-templates). A link <page>.html#view=<id> opens an entry in display mode, #edit=<id> in the form; "Open" in the table of another page takes #view= if the target entity may not be changed.
    • Answers: not signed in: the API answers 401 (JSON), a page redirects to login.html; signed in without the right: 403; what the entity does not allow at all: still 405. GET /api/me returns {name, roles, mustChangePassword, permissions}; the pages use it to show only the buttons and forms the role needs, and at the top right of the navigation a hamburger menu (☰) with "Signed in as …", "Change password" and "Sign out" (closes with Esc or a click outside).
    • Passwords exist nowhere in plain text, and in security.yml there are none at all (since 0.13.0). A user starts with the password equal to the name (admin/admin, user/user: publicly known, for development only); the application hashes it at start. If a user should start with another one, there is an optional password: with a bcrypt hash ($2b$10$…); generate and the application reject an entry whose password is not a hash.
    • Where the files are: Spring: src/main/resources/security.yml (classpath, in the jar: change and restart or build), Hono: security.yml in the project folder (change and restart). The chosen passwords are not in a file but in the table usr_password of the application's database (name, bcrypt hash; Spring creates it at start with CREATE TABLE IF NOT EXISTS, Hono has the Prisma model UsrPassword).
    • First login: with mustChangePassword (default: true unless false is there) you get the page change-password.html after logging in, where the new password is entered twice (at least 8 characters, at most 72 bytes, not the user name). Until then the application answers everything else with 403 password change required. The hash of the new password ends up in the table usr_password; security.yml stays unchanged, with all its comments. Later you change it in the menu (☰) via "Change password". Forgotten: deleting the user's row in usr_password resets to the start password. With H2 in memory the table is empty after every restart (then start password and forced change apply again); with PostgreSQL and SQLite the password stays. Moving up from 0.12.x: init --force deletes the old security.yml in the project folder (Spring, if unchanged) and reports passwords.yml; the passwords chosen earlier no longer apply.
    • Your own user or hash: pisa hash-password asks for the password twice without echo (or --stdin; never as an argument, the shell would keep it) and prints the bcrypt hash that you enter as password:. bcrypt exists in Java (BCryptPasswordEncoder) and in JavaScript (bcryptjs): the same file works in both targets.
    • Session: cookie, with Spring with a CSRF token (the pages send X-XSRF-TOKEN), with TypeScript HttpOnly and SameSite=Lax. H2 console (Spring): for ADMIN only.
    • Tests: the generated tests sign in as test users that are not in your security.yml but in a test file (src/test/resources/security-test.yml or test/security-test.yml, written by generate, hashes only): tester may do everything the entities allow, nobody nothing, newcomer and newbie have to choose a password. SecurityTest or test/api/security.test.ts check 401/403, the form, /api/me and setting the password (the file written has only a hash); a browser test goes through the first login. Per role of the .adl there is a test user as-<role> in the test file (as-admin, as-user); RolesTest or test/api/roles.test.ts check for every role and every entity what /api/me lists, that an allowed operation does not end in 403 and a disallowed one does (create, read, update, delete; what @operations does not allow at all is missing: that is the 405). The tests follow the roles of the .adl, not a security.yml changed by hand.
    • Back to "no login": remove the line from the .adl, init … --force and generate. The login files (SecurityStore, SecurityConfig, EntityAccess, SecurityController, the pages or src/lib/security.ts) are deleted if you have not changed them (otherwise they stay and are reported with the rm command, see 4c); they need Spring Security or bcryptjs, which pom.xml/package.json then no longer have. security.yml and passwords.yml stay yours.

    Not possible: creating or managing users in the browser, resetting a password by e-mail, tokens (JWT) or external providers (Keycloak/OIDC), rights per field or row, HTTPS (the password goes over the wire in plain text at login as long as the application runs over HTTP: development), limiting login attempts.

    4e. Describing the architecture (spec/*.adl, optional)¶

    Instead of writing .pisa/architecture.plan.json by hand, you can describe the architecture in an .adl file (language of the Pisa plugins, with colors, errors, completion and formatting). It is structured by the C4 levels: containers (database, backend, frontend) and in the backend the components (crud or layered); the code is the .dml.

    architecture Library {
    container main : database {
        engine postgresql          // h2 (runtime spring only) | sqlite (runtime hono only) | postgresql
        name library
    }
    container api : backend {
        runtime spring             // spring (default) | hono, see 4f
        package ch.ffhs.cas.library
        uses main                  // the database of this backend
        components layered         // crud | layered
        versions { archunit "1.6.0" }
    }
    container web : frontend {
        servedBy api               // embedded: the backend serves the pages
    }
    scm {                          // optional: templates for GitHub, see below
        host github
        pullRequestTemplate
        issueTemplates
    }
    pipeline {                     // optional: workflows in the project, see below
        ci github
        release github
        deploy render              // optional: Render, needs the docker block
    }
    docker {                       // optional: Dockerfile and compose.yml, see below
        image "library"
        compose
    }
}

    pisa init --target spring-boot --out ./library --adl library.adl

    init reads the file (errors stop before writing, with file, line and column), copies it to spec/library.adl and derives from it:

    In the .adl Effect
    runtime spring\|hono the target (spring-boot / hono-prisma); if missing, --target applies, otherwise spring-boot
    authentication session login with users and roles (security.yml, see 4g); without the line: no login, everything open
    roles { ADMIN USER { Company: read, update } } the roles and their rights (plan.roles): init writes security.yml from it, generate the tests per role; only with authentication session; without the block: ADMIN and USER, both may do everything
    components crud\|layered style in the plan
    Database that the backend names with uses database.engine and name; for PostgreSQL without an earlier password the development login app / app is entered
    versions { … } the versions named, in the plan; the others stay
    package base package of the project (project.spec.json); --package must not contradict
    pipeline { ci github release github deploy render } init writes .github/workflows/ci.yml, release.yml and with deploy render render.yml and cd.yml (plan.pipeline), see below; each line on its own, without it the files are missing
    docker { image "…" compose } init writes Dockerfile and .dockerignore (plan.docker) and with compose the compose.yml, see below; without the block nothing is created
    scm { host github pullRequestTemplate issueTemplates } init writes .github/pull_request_template.md and .github/ISSUE_TEMPLATE/ (plan.scm), see below; the two templates need host
    frontend documentation only: the pages are always embedded

    What the file does not name (packages, ports, users, console …) stays as it is in the plan. pom.xml and application.yml are created once at init. That is why generate only checks whether the project still matches the .adl. If you changed it, it stops with the differences (style: plan layered, library.adl says crud) and says how to go on: pisa init … --adl spec/library.adl --force rewrites plan and bootstrap files. A project has at most one .adl. It is in the recipe (init and generate), replay restores it.

    CI workflow (pipeline, since 0.13.0): With pipeline { ci github } init writes the file .github/workflows/ci.yml into the project. It runs on every push to main and on every pull request, with two separate jobs so that the slow browser tests do not hold up the fast ones:

    Target Job tests Job browser-tests
    Spring mvn -B test (Java version from --java, Temurin, Maven cache); with PostgreSQL mvn -B test -Ptestcontainers (the GitHub runners have Docker; the job takes a bit longer) install the Playwright browser, then mvn -B test -Pui
    Hono npm install, npm run typecheck, npm test (Node 24); with PostgreSQL a postgres service with the details from the plan npx playwright install --with-deps chromium, npm run test:ui

    The file is created once and then belongs to you: even init --force does not overwrite it. The word after ci is a name that the editor checks; today there is only github (others such as gitlab report an error). Pisa has not yet run the file on GitHub: whether the jobs turn green there (above all the browser tests, Spring -Pui) is unchecked.

    Release workflow (release github in pipeline, since 0.13.0): init writes .github/workflows/release.yml. It runs when you push a tag like v1.0.0 (git tag v1.0.0 && git push origin v1.0.0): with Spring mvn -B package (runs the unit tests) and gh release create with the automatically generated notes and the JAR file as an attachment; with Hono typecheck and npm test (with PostgreSQL the postgres service) and a release with the notes, without an attachment (the project builds nothing). Without ci the editor reports a warning: the tests then run only at the tag, not on every push. Like ci.yml the file is created once; it has never run on GitHub.

    Templates for GitHub (scm, since 0.13.0): The scm block says where the repository lives (host github, today the only value) and which templates belong to it: pullRequestTemplate writes .github/pull_request_template.md (description, changes, a checklist with the test command of the target and the hint to change spec/ instead of the generated code), issueTemplates writes .github/ISSUE_TEMPLATE/bug_report.yml and feature_request.yml (GitHub forms) and config.yml (blank_issues_enabled: false). Both lines need host, because the location depends on it (otherwise an error), and each line is on its own: only what is there is created. All files are created once and then belong to you. GitHub checks the forms only when they are uploaded; Pisa has tested them only as valid YAML with the required entries. host, ci and release must name the same system (otherwise an error). New keywords of the .adl are pipeline, ci, release, scm, host, pullRequestTemplate, issueTemplates, docker, image and compose: they no longer work as part of a package name (package io.github.x still does).

    Docker (docker, since 0.13.0): The block belongs to the application and is independent of whether it later runs in the cloud. docker { } alone writes Dockerfile and .dockerignore; image "<name>" names the image (default: the artifactId; a text, because names have hyphens; lower case letters, digits, ., _, -, / for a path, no tag, otherwise an error in the editor); compose additionally writes the compose.yml (the default name Docker looks for first, so no -f). With engine postgresql the compose.yml with the application (app) and the database (db) is created even without compose (an image alone would not find the database); with H2 and SQLite compose stays your choice, one container is enough there. Without the block nothing is created, and an existing compose.yml (PostgreSQL only) stays as it is. The files:

    File Spring Hono
    Dockerfile two stages: maven:3-eclipse-temurin-<Java> builds the JAR file (mvn package without tests), eclipse-temurin:<Java>-jre runs it (Java version from --java); user app, port 8080; with H2 the TCP server is switched off (security.yml is in the jar) node:24-slim (Debian: better-sqlite3 is native), all dependencies (prisma is needed at start), prisma generate, user node, start with npm start; with SQLite the file is in /data
    .dockerignore target, .git, .pisa, doc among others the same with node_modules and the SQLite files
    compose.yml (with compose) service app (build: ., image, port 8080; Hono with volume /data for the SQLite file); with PostgreSQL the service db (health check, app waits for it) and the environment SPRING_DATASOURCE_* the same with DATABASE_URL

    With Hono /data in the container is a volume for the SQLite file (the chosen passwords stay with it); Spring needs no volume (H2 in memory: a chosen password is gone with the container; with PostgreSQL it is in the database). Users and roles (security.yml) are part of the image (with Spring in the jar): rebuild after a change. docker compose up --build starts everything; only the database (for developing with mvn spring-boot:run or npm start): docker compose up -d db. Dockerfile and .dockerignore are created once and then belong to you (even init --force does not overwrite them); the compose.yml comes from the plan as before and is rewritten by init --force. The host port 8080 is fixed in the compose.yml; if it is taken, change it there ("8081:8080"). The generated README.md has a section "Run in Docker".

    Checked (2026-10-22, by hand and as PISA_IT=docker bun test test/generated-project-docker.test.ts): image built and container started for Hono with SQLite and Spring with H2; docker compose up --build for Hono and for Spring with PostgreSQL (application and database, tables created, an entry saved through the interface); the login works in the container (checked once more after the switch to the table usr_password on 2026-10-22: Spring with H2, Hono with SQLite and volume; there the chosen password applies after a restart of the container). Stumbling block on the Mac: Docker Desktop's credential helper can hang when looking up a base image (a hanging process docker-credential-desktop get); then a DOCKER_CONFIG folder whose config.json has no credsStore helps. If you switch the database of a Spring project from H2 to PostgreSQL, the old H2TcpServerConfig.java breaks the build in the image as it does elsewhere; init --force deletes it itself if it is unchanged (see "Switching the database").

    Cloud: Render (deploy render, since 0.13.0). pipeline { deploy render } runs the application as a Docker image on the free web service of Render. The docker block is required (without it an error in the editor: there is no image); deploy may stand next to host github, the value says where the application runs, not where the repository is. init then writes two files, once, after that they belong to you (even init --force does not overwrite them):

    File Content
    render.yml the blueprint: type: web, runtime: docker, plan: free, region: frankfurt, dockerfilePath: ./Dockerfile, autoDeployTrigger: "off", healthCheckPath (/login.html with login, otherwise /), PORT=8080; Spring additionally JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75; with PostgreSQL the connection as environment variables with sync: false (Render asks for them when creating)
    .github/workflows/cd.yml on a tag v* a job calls the service's deploy hook (curl to the secret RENDER_DEPLOY_HOOK_URL, with &ref=<commit>); if the secret is missing, it aborts with a hint

    Only the hook deploys, so only releases (with release github a tag v… creates the release, cd.yml starts on the same tag). The first time by hand: (1) push the project to GitHub, (2) on dashboard.render.com New ▸ Blueprint, pick the repository and enter render.yml in the field Blueprint Path (Render looks for render.yaml by default; that it finds render.yml by itself is not in the documentation), (3) in the service Settings ▸ Deploy Hook copy the URL and save it in the repository under Settings ▸ Secrets and variables ▸ Actions as RENDER_DEPLOY_HOOK_URL (the URL is secret, Pisa never writes it into a file), (4) set a tag. pisa init prints the pointer to the comments at the top of render.yml.

    The limits of the free service (Render documentation, 2026-10-22): it sleeps after 15 minutes without requests (waking up takes about a minute), has 750 instance hours a month and no persistent disk: H2 and SQLite live in the container and are gone after every restart and sleep (the chosen passwords too). Render's free PostgreSQL expires after 30 days; deploy render with engine postgresql therefore gives a warning, and the blueprint creates no database: you give it the connection of your own. Why Render: other free offers require a card (Koyeb since February 2026 according to search results) or a billing account (Google Cloud Run, whose free quota is larger: 2 million requests, 180,000 vCPU-seconds and 360,000 GiB-seconds a month according to the price page). Not checked: a real deploy (start, whether 512 MB are enough for Spring, whether the port 8080 and the healthCheckPath behind the login are right, whether render.yml is found without entering the path).

    Git repository: If the .adl has a pipeline or scm block, or you pass --git, init creates a Git repository in the project folder (git init -b main) and makes the first commit in it (Initial project (pisa init), after the recipe, so with .pisa/recipe.json), local only: no remote, no push, because Pisa does not know your account. Name and e-mail come from your Git configuration, Pisa sets nothing. If they are missing, or Git refuses the commit (signing, hook), there is no commit, and init prints git add -A and git commit -m "Initial project"; it does not end with an error. After that comes the pointer to the way to GitHub: gh repo create <name> --private --source . --push. The commit contains the scaffold after init; the code from generate you then see as a change. If the folder is already in a Git working tree (for example under samples/), it is left alone, and with init --force in an existing repository there is no commit; if git is missing, init says so and goes on. Without --git and without the blocks nothing changes.

    The repository on GitHub (example, by hand): Pisa only creates the local repository; you take it to GitHub yourself, in a folder without a repository with the first command, otherwise without it:

    git init -b main                      # only if Pisa did not create a repository (without --git and without pipeline or scm)
git add -A                            # likewise: only if there is no commit yet
git commit -m "Initial project"
gh repo create <name> --private --source . --push     # creates the repository (private) and uploads; needs `gh auth login`

    Without gh: create an empty repository on github.com, then git remote add origin git@github.com:<your-name>/<name>.git and git push -u origin main. For GitLab, Bitbucket and Codeberg it is the same git commands with the address of the respective repository; Pisa has no support of its own for them.

    Name of the application: The start page shows as its heading (and as the title of the browser tab) the name from app.title in application.yml, not the artifact id. init writes it once: the name after architecture in the .adl (architecture Adressen { gives "Adressen"), without --adl the artifact id. To change it: change the value in application.yml and restart the application, no generate is needed. The page fetches it from GET /api/app; if the entry is missing, the application is called "Application". With Spring init … --force rewrites the application.yml (database and name then come from plan and .adl again); with the TypeScript target (application.yml in the project folder) init never overwrites it.

    Not possible: several backends or databases, gateway, broker, hexagonal, assigning entities to a backend (the validator rejects more than one backend).

    Switching the database (H2 → PostgreSQL): engine postgresql in the .adl, then init --adl … --force and generate. The file src/main/java/…/config/H2TcpServerConfig.java (imports org.h2.tools.Server, breaks the build with "Package org.h2.tools does not exist") is deleted by Pisa itself, if you have not changed it (since 0.13.0; before that you had to delete it by hand). The same when switching the style layered → crud for the folders dto/, mapper/ and service/ (and src/test/…/service/): they need Lombok and MapStruct, which the new pom.xml no longer has. First init --adl … --force and generate: init cleans up the start files (compose.yml, H2TcpServerConfig.java), generate the files per entity. The rule: Pisa deletes a file only if it looks exactly like what it wrote itself (the hash in the recipe .pisa/recipe.json matches) and the plan no longer wants it. It reports Info: deleted, no longer used by .pisa/architecture.plan.json and unchanged since Pisa wrote them: with one file per line, and the recipe remembers the deletion (replay still matches). A file that you changed (or that no step recorded) stays; this also holds for Java files that Spotless reformatted during the Maven build (not all generated classes are formatted already, the main class and H2TcpServerConfig were in the trial) and is listed under Info: no longer used … changed by you with the line Delete them with: rm …; you delete those yourself. init also cleans up files under src/ that an earlier init run wrote and the current one no longer writes, above all the class <Name>Application after a change of the artifactId (two main classes break mvn package with "Unable to find a single main class"), and a compose.yaml from the time before compose.yml. The compose file is called compose.yml (the short extension; docker compose finds it without -f, checked). What else is not deleted is in "Not yet possible".

    JDBC URL jdbc:h2:mem:<artifact>
    User sa
    Password empty (the H2 defaults, written into application.yml under spring.datasource)

With login (authentication session, 4g) you first see the application's login page: sign in with the role ADMIN (other roles get 403, the console shows all tables); after that comes the console's own login. Until 0.13.0 the console stayed unusable with login (the "Connect" button answered 403 because of the CSRF check, and the frames of the console were blocked by X-Frame-Options: DENY).

    4c. The architecture plan (.pisa/architecture.plan.json)¶

    What the structure of the generated project depends on is no longer in the templates but in a small file that init creates and generate reads:

    {
  "version": 1,
  "style": "crud",
  "packages": { "model": "model", "repository": "repository", "controller": "controller", "validation": "validation", "ui": "ui" },
  "versions": { "springBoot": "4.1.1", "alpinejs": "3.17.4", "validator": "13.12.0", "bootstrap": "5.3.8", "playwright": "1.63.0",
                "archunit": "1.5.1", "spotless": "3.10.4", "palantir": "2.102.0", "commonsValidator": "1.11.0",
                "postgres": "17", "mapstruct": "1.6.3", "lombokMapstructBinding": "0.2.0" },
  "database": { "engine": "h2", "user": "sa", "password": "", "console": true,
                "tcp": { "enabled": true, "port": 9092 }, "port": 5432 }
}
    • packages: package names below the base package (<base>.model etc.); lower case letters and digits, with a dot for subpackages (web.rest), no Java keyword.
    • versions: everything the build loads. They end up in the pom.xml (as properties at the top) and in the pages (paths of the WebJars). The values above are an example: what a new project gets is in Pisa's source code and changes with every version; an existing project is brought to the newest stable versions by pisa update-versions.
    • database: which database and how to log in. engine is h2 (in memory, default with Spring), sqlite (a file, default with Hono; only with runtime hono, with Spring the .adl reports an error) or postgresql; name (optional, default: the artifactId), user, password (not empty for PostgreSQL). H2 only: console (H2 console under /h2-console) and tcp (port for IntelliJ). PostgreSQL only: port (on this machine; compose.yml maps it to 5432 of the container). All of it ends up in application.yml, pom.xml, the test properties and possibly compose.yml; versions.postgres is the image in compose.yml.
    • PostgreSQL: driver in the pom.xml (runtime only), compose.yml (docker compose up -d), in application.yml ddl-auto: update (a server keeps its tables), no H2 console and no TCP server. The tests still run without Docker on H2 in PostgreSQL mode, one context per database. Checked with a real container (postgres:17): the application starts, creates the tables, a row created through the API is in psql, and a duplicate value (409) and a missing required field (400) arrive as with H2 (SQL state).
    • authentication: "session" switches the login on (missing: no login, everything open); roles (only with authentication): role → entity (or "*") → operations, the form of security.yml that init writes from it; both come from the .adl (roles { … }, see 4g) and are missing without it (then ADMIN and USER apply, both may do everything).
    • style: crud (default: controller → repository, the entity is the JSON) or layered: controller → service → repository, plus per entity a DTO (dto, Lombok @Data) and a MapStruct mapper (mapper). The DTO is the image of the entity (same fields, references and parts as nested DTOs, the inverse side is missing as with @JsonIgnore), so the JSON and with it the page stays unchanged; the rules of the fields (Bean Validation) are on the DTO. The service (@Transactional) maps and talks to the repository; parts get DTO and mapper, but no service. ArchitectureTest checks the layers, ServiceTest per root the mapping in both directions. Spring Boot manages Lombok; MapStruct (1.6.3, the last stable one; 1.7.0 is still beta) and the Lombok binding are properties in the pom.xml, the annotation processors in the maven-compiler-plugin configuration. Checked with two models (also manyToMany, string ids, parts): the same HTTP and browser tests as with crud pass, and a violation of the layers (controller → repository) turns ArchitectureTest red. The style belongs in the plan before init (pom.xml); a later switch needs init --force, and files of the earlier style stay.
    • Pisa checks the file against a schema; an invalid file stops generate without writing anything. A project without a plan (older) takes the default plan and gets none written.
    • The plan is an input in the recipe; replay brings a changed plan along.
    • Order: change the plan before init runs (create the file, then init; init takes an existing plan and never overwrites it). After that package names and versions affect generate; the pom.xml and the GlobalExceptionHandler come from init and follow only after init --force. Files of an earlier package structure stay (Pisa does not delete them, the plan does not know them) (e.g. a second GlobalExceptionHandler and both packages at the same time lead to a bean conflict) and have to go by hand. When the database is switched, init/generate delete files that the plan no longer wants and that you did not change ("deleted, no longer used by .pisa/architecture.plan.json"), e.g. the H2 TCP class after the switch to PostgreSQL (it no longer compiles there); changed files it reports with the ready rm command (Delete them with:). The switch itself: change the plan, then pisa init --force (rewrites pom.xml, application.yml, compose.yml; README and plan stay), delete the files reported, generate.
    • Later an LLM proposes this plan from the architecture description; the file is the format for it.

    4b. Versions and formatting in the pom.xml¶

    All versions that the Spring Boot parent does not manage (Alpine.js, validator.js, Bootstrap, Commons Validator, ArchUnit, Playwright, Spotless, Palantir Java Format) are properties at the top of the pom.xml (<alpinejs.version> etc.); whoever changes a version changes it only there. Spotless formats with Palantir Java Format at every build (phase process-sources) all Java files, the generated ones too; without a build use mvn spotless:apply. Consequence: after a build the generated files in the project differ from what the recipe records. That does not disturb pisa replay (it checks the freshly generated files), and the next generate writes them unformatted again, the next build formats again.

    Keeping versions current: not by hand in the properties, but with pisa update-versions: it fetches the newest stable versions (Maven Central), tries them on a copy of the project and writes what passes into the versions { } of the .adl.

    5. Describing the form as a spec (optional)¶

    Without further statement every page gets a default form (all fields one below the other, English). How a form should look you describe in spec/<entity>.ui.md. The shortest way without an LLM is a Salt mockup (PlantUML) in this file: the mockup is the layout, generate reads it deterministically.

    pisa propose-layout --entity Customer --out .

    This creates spec/customer.ui.md with a starting text that lists the fields of the form, and stops (exit 0). Replace the content with a description with a mockup:

    # Form: Customer

Name and e-mail side by side, below them the purchases as a table.

```plantuml
@startsalt
title Customer
{+
  {^"Customer"
    Name | "name" | E-mail | "email"
  }
  {^"Purchases"
    Purchases
    {#
      Date | Paid
      purchases.orderedAt | purchases.paid
    }
  }
  [Save] | [Cancel]
}
@endsalt
```

    Then generate again; generate reads the mockup directly (a separate step for it is not needed):

    pisa generate --file spec/shop.dml --out .

    The page customers.html now has the title "Customer", labels as in the mockup, name and e-mail on one line, the purchases as a table with paging and the buttons "Save"/"Cancel". There is no second file with the layout (see Forms). If the mockup later no longer matches the model (field added or removed), generate aborts with the line and writes nothing.

    Instead of writing the .ui.md and a .uc.md yourself, you can have them derived from the model: pisa propose-specs --out . (without an LLM, see Commands). After that generate: the pages follow the mockups, and for every use case (spec/use-cases.uc.md, see "Use cases: .uc.md") a browser test is generated.

    6. Reproducing (optional)¶

    Every step was recorded in .pisa/recipe.json and in the README.md of the project. From the recipe the project can be rebuilt in an empty folder and checked:

    pisa replay --from ./shop --out ./shop-copy

    At the end it says All N generated file(s) match the hashes recorded in the recipe.

    The result at a glance¶

    shop/
  project.spec.json            spec: target and options             (from init)
  spec/shop.dml                spec: domain model                   (from you)
  spec/customer.ui.md          spec: form description + mockup      (from you)
  .pisa/recipe.json            recipe of all Pisa steps             (from Pisa)
  pom.xml, src/…               the Spring project                   (init/generate)

    Rule of thumb: you write spec/, .pisa/ belongs to Pisa. project.spec.json and README.md are project files (Pisa writes the README only between its markers).

    The concept in one minute¶

    Pisa deliberately separates two things:

    • The skeleton (entities, relations, REST routes, one input element per field type) is deterministic: templates and model in, text out, no LLM. Same input, same output.
    • The flesh (grouping, order, labels of a form) comes from a description that you write. Pisa reads the layout from the Salt mockup in it, or an LLM proposes one (propose-layout), which Pisa checks and writes into the same document as a mockup. There is no second model next to it.

    The specs are the source of truth, the code is derivable:

    Spec File Who writes it
    Project (target, options) project.spec.json pisa init
    Domain model spec/*.dml you; propose-model can propose it from spec/domain-spec.md or spec/requirements.md
    Architecture (optional) spec/*.adl you; pisa init --adl derives the plan from it; propose-architecture can propose it from spec/architecture.md or spec/requirements.md
    Form (prose and mockup = layout) spec/<entity>.ui.md you; a proposed mockup is written into it by pisa propose-layout
    Template overrides .pisa/templates/<target>/ you (eject-templates)

    Commands¶

    pisa --help / -h shows the overview with a quick start, pisa <command> --help (also pisa help <command>) options and short examples of a command; help runs nothing. pisa --version / -v shows the version and build time. Short forms: -f/--file, -e/--entity, -o/-d/--out. "Existing files are never silently overwritten" holds for init and eject-templates (with --force they are).

    Display that Pisa is working: On a terminal Pisa shows, during proposals (propose-architecture, propose-model, propose-layout, as long as the model answers) and during generate and init, a symbol with text and seconds, for example ⠙ Proposing the architecture 12s. With generate and init it appears only after 0.4 seconds, a quick run shows nothing. The text the model streams stands normally above it; the symbol disappears at the end. Not when redirected to a file or pipe, not with CI set and not with PISA_NO_SPINNER=1.

    pisa init¶

    pisa init [--out <dir>]                 # without target and .adl: only doc/ and spec/
pisa init [--target spring-boot|hono-prisma] --out <dir> [--group <groupId>] [--artifact <artifactId>]
          [--package <base.package>] [--java 17|21|25] [--adl <architecture.adl>] [--templates <dir>] [--git] [--force]

    Without --target and without --adl pisa init (the target folder is then ., or --out) creates no project yet: only the folder doc/ with this user guide and both tutorials and an empty folder spec/. That is the start of the tutorials: there you decide whether Java (Spring Boot) or TypeScript (Hono) should be built. With --target or --adl init creates a startable project and project.spec.json and also copies doc/ (existing files there stay without --force; the documents are not part of the recipe). --group, --artifact, --package, --java, --templates and --git exist only with --target or --adl.

    Option Meaning Default
    --target target: spring-boot (Java) or hono-prisma (TypeScript). With --adl it may be missing: then runtime of the file applies spring-boot if runtime is missing too
    --out target folder –
    --group Maven groupId –
    --artifact Maven artifactId name of the target folder
    --package base package <group>.<artifact without hyphens>
    --java Java version 25 (current LTS)
    --adl architecture description (.adl): sets target (runtime), style, database, versions and base package; copied to spec/ (see 4e) –
    --templates own folder with template overrides <out>/.pisa/templates/<target>/ if present
    --git make the folder a Git repository (git init -b main) with a first local commit; also happens if the .adl has a pipeline or scm block; in the recipe (--git); no effect in an existing repository off
    --force overwrite existing files (the README.md never) off

    Re-initializing an existing project with --force also rewrites pom.xml and the other bootstrap files.

    pisa play¶

    pisa play <spring-java | hono-typescript | file.md> [--dir <folder>] [--llm] [--fast] [--yes] [--dry-run] [--from <n>] [--to <n>]
pisa --play <tutorial> ...                 # the same

    Plays a tutorial: runs its commands, writes the files it shows, starts the application and asks it for the login page, and reports step by step ✓ or ✗. pisa play hono-typescript (or spring-java) takes the bundled tutorial and needs no file even with the installed binary.

    • Without a name (pisa play) Pisa names the tutorials and how to begin. A file that is an unchanged tutorial from Pisa (the copy in doc/ that pisa init wrote) counts as trusted and runs without asking; an edited or foreign file asks.
    • Folder: the current folder (or --dir <folder>). The tutorial creates its project itself as a subfolder, as it says in the text (adressen-hono/). What the tutorial creates only for checking, the copy of the replay (adressen-hono-copy/), Pisa deletes again at the end (only inside the folder it plays in); the project stays, and Pisa names it. Other files in the folder do not matter (after pisa init there are doc/ and spec/), but the subfolder the tutorial creates must not exist yet: otherwise Pisa aborts beforehand. With --from <n> you can go on after an abort (--dir to the folder in which step n should work).
    • Without a language model (default): the steps that would need the model (propose-architecture, propose-model) are skipped; Pisa writes the files the tutorial shows as the result instead. Fast, free, repeatable. With --llm it really asks the model (pi must be set up). --fast leaves out everything that takes long: all tests (mvn test, npm test, the browser tests), starting the application, reproducing (pisa replay) and the optional steps (marker optional, in the tutorials step 10: CI); what remains is creating the project, deriving specs and generating code (the fastest run, a few seconds). --dry-run only shows the course.
    • Beforehand: Pisa shows the course and checks whether the programs of the commands are there (node, npm, java, mvn, …); if one is missing, nothing runs. With your own file it asks before the run (--yes skips), the bundled tutorials count as trusted.
    • pisa in the commands is this Pisa, not one that happens to be installed. The server runs on a free port; the spinner names what is happening (Maven loads and compiles, Spring starts, Prisma creates the tables) (PORT and SERVER_PORT are set; H2_TCP_ENABLED=false switches off Spring's H2 TCP server on its fixed port 9092, so that an application that already runs on your machine does not interfere); browser steps and manual changes (7a) stay manual and are only listed.
    • On an error the run stops, names step and line of the tutorial, and what had been created stays. Every command of a block is checked on its own (also mkdir x && cd x: if the mkdir fails, nothing goes on in the wrong folder). The exit code of the commands is checked, not the text "You should see".

    For tutorial authors: a tutorial is Markdown; every ```bash block is a command, and an HTML comment directly before a block says what applies otherwise (invisible when reading):

    Comment Effect
    <!-- play: write spec/a.md --> the block is the content of this file
    <!-- play: write spec/a.adl unless-llm --> the same, but only without --llm (the result shown of a model step)
    <!-- play: llm --> the next bash block runs only with --llm
    <!-- play: tests --> the next bash block runs tests (mvn test, npm test): it is dropped with --fast
    <!-- play: slow --> the next bash block (the browser tests, the replay) is dropped with --fast
    <!-- play: optional --> the next bash block belongs to an optional step (for example the CI at the end of the tutorials): it runs, but is dropped with --fast
    <!-- play: skip --> the block is not run, only listed as "by hand"
    <!-- play: server /login.html --> the block is a command that starts the application; Pisa waits until the path answers (PORT, SERVER_PORT and H2_TCP_ENABLED=false are set), and ends it; dropped with --fast

    All other blocks (expected files as examples, yaml, json) are text. An unknown comment or a comment without a block is an error with a line number.

    pisa generate¶

    pisa generate --file <model.dml> --out <dir> [--target <name>] [--templates <dir>] [--force]

    Generates the files per entity (JPA, repository, controller, page) and the model-wide frontend files. The target comes from --target, otherwise from <out>/project.spec.json.

    • The model belongs to the project: --file /somewhere/shop.dml copies the file to <out>/spec/shop.dml. Pisa does not silently overwrite an existing file of the same name that differs (take the project copy or --force).
    • Several model files: all .dml in <out>/spec/ are read together ("Info: reading the project's other model file(s) too"). If file A, which refers to B, is not yet in spec/ together with B, Pisa reports Could not resolve reference — first put all files into spec/, then generate.
    • The files are rewritten on every run, nothing is ever deleted (not even after renaming an entity).
    • If the spec/<entity>.ui.md of an entity has a Salt mockup, it determines the form. If the mockup no longer matches the model, generate aborts before anything is written; then adjust the mockup or have a new one proposed with propose-layout.
    • A part (composed) gets only its JPA class, no page of its own and no controller of its own.
    • Without project.spec.json and without --target Pisa falls back to the older target prisma-hono-ink and says so with an Info: line. For Spring always init first.

    --file is required: the model is the .dml. The earlier short form with --entity/--fields/ --relation and the derived .pisa/entities/*.json no longer exist (in earlier projects generate reports them as "no longer used"; deleting is up to you).

    pisa propose-architecture¶

    pisa propose-architecture --out <dir> [--force]

    Has an LLM propose an architecture description from the prose in spec/architecture.md and writes it as spec/architecture.adl (format: section 4e). It applies nothing: the project is created or changed only with pisa init --adl.

    Situation Result
    no spec/architecture.md or still the starting text (marker pisa:starting-text), and no spec/requirements.md either creates it with questions or aborts, no LLM call, exit 0
    no filled-in spec/architecture.md, but a spec/requirements.md (since 0.10.0) the LLM reads this and takes only what concerns the architecture (runtime, style, database, login, package, versions); the recipe names spec/requirements.md as an input
    a spec/*.adl exists already nothing (exit 0); with --force it is proposed anew, into the same file
    description filled in the LLM proposes (needs pi access); the file is in spec/ afterwards, the step in the recipe
    more than one .adl in spec/ refused
    the LLM does not answer through the tool or fails three times exit 1, nothing written

    One text for both (spec/requirements.md, since 0.10.0): Whoever wants to describe requirements as a whole (what the application can do, for whom, with which technology) writes them in spec/requirements.md. propose-architecture and propose-model read this file if their own description is missing or still the starting text; a filled-in architecture.md or domain-spec.md always takes precedence (the human wrote it for exactly this command). Each command takes only its part (architecture: runtime, style, database, login, package, versions; model: entities, fields, relations, value rules); what does not fit goes into notes. There is no command that does both in one go: first propose-architecture, then propose-model, checking each. An empty file counts as absent. Pisa never creates requirements.md itself.

    The LLM sees the description and, if present, the entities of the model (spec/*.dml); it may answer only through a checked tool: style crud|layered, runtime (spring|hono), login (authentication session, only if the description mentions login, users, passwords or roles), roles with their rights (roles, only if the description mentions them), database h2|postgresql (with name), base package, versions. Every answer is checked as in the IDE (the same parser and validator, plus plan schema); a wrong one goes back to the LLM with the message, at most three attempts. Versions from memory are rejected: the LLM must look them up with lookup_version at Maven Central (stable version, no beta/RC/milestone), and the file names the date and the source in its header. Wishes that an .adl cannot express stand as // Not covered: … above architecture.

    Then: new project pisa init --target spring-boot --out <dir> --adl spec/architecture.adl, existing project the same with --force. Set up LLM access as for propose-layout.

    pisa propose-model¶

    pisa propose-model --out <dir> [--name <name>] [--force]

    Has an LLM propose a domain model from the prose in spec/domain-spec.md and writes it as spec/<name>.dml (name: --name, otherwise the project name). It creates nothing else: check the file, then pisa generate.

    Situation Result
    no spec/domain-spec.md or still the starting text (marker pisa:starting-text), and no spec/requirements.md either creates it with questions or aborts, no LLM call, exit 0
    no filled-in spec/domain-spec.md, but a spec/requirements.md (since 0.10.0) the LLM reads this and models only what concerns the data; technology, database and login it leaves out or names under notes; the recipe names spec/requirements.md as an input
    spec/<name>.dml exists already nothing (exit 0); with --force it is proposed anew, into the same file; with --name <other> a second model file is created
    description filled in the LLM proposes (needs pi access); the file is in spec/ afterwards, the step in the recipe
    the LLM does not answer through the tool or fails three times exit 1, nothing written

    The LLM sees the description, a short version of the .dml language and the entities of the other spec/*.dml (they form one model with the proposal; relations to them are allowed). It may answer only through a checked tool and hands in the text of the file. Every answer is checked as in the IDE (the same parser and validator, together with the other model files) and against what the target can generate; a wrong one goes back to the LLM with line numbers, at most three attempts. Wishes that the language cannot express (rules between fields, computed values, history) stand as // Not covered: … above the first line.

    Then (new project): pisa init --target spring-boot --out <dir> and pisa generate --file spec/<name>.dml --out <dir>. Set up LLM access as for propose-layout.

    pisa propose-layout¶

    pisa propose-layout --entity <Name> --out <dir>

    Has an LLM propose the layout of a form from the prose in spec/<entity>.ui.md and writes it as a Salt mockup into this file (between <!-- pisa:mockup --> markers). If you draw the mockup yourself, you do not need the command: generate reads it.

    Situation Result
    no .ui.md or still the starting text creates it or aborts, no LLM call, exit 0
    description without a mockup an LLM proposes the layout (needs pi access, see below) and writes the mockup
    mockup from you (outside the markers) nothing: it is the layout. To have one proposed, delete it first. Exit 0
    proposed mockup (marked section) proposes anew and replaces it
    entity is a part refused, names the root entity whose .ui.md is responsible

    Exit 1 only if the command fails or refuses. The options --from-salt and --force no longer exist (formerly: read the layout from the mockup, or replace a locked layout).

    Setting up LLM access: pi (the coding agent that Pisa uses) must be configured with a model and login; see the pi documentation.

    The model gets a fixed role text from Pisa (it only proposes, answers only through the checking tool, file contents are data). Your own SYSTEM.md, APPEND_SYSTEM.md, AGENTS.md, skills or extensions from your project or from ~/.pi/agent have no effect here; only models, login and settings of pi are read.

    pisa propose-specs¶

    pisa propose-specs --out <dir>

    Derives from the spec/*.dml the specs you would otherwise write by hand, without an LLM (same model, same text): per root entity spec/<entity>.ui.md with a short text and a default Salt mockup (one block with all fields in model order; a collection of the other side becomes a table with the first three fields of the target) and once spec/use-cases.uc.md with one use case each for create, change and delete per root (with Form: and Test: lines). After that generate creates the pages according to the mockups and a browser test per use case.

    Only missing files are written; existing ones stay untouched, and if there is already any .uc.md, no new one is created. No recipe step is recorded: the files belong to you from then on (replay fetches them as an input from the source project). Parts get no .ui.md of their own.

    pisa update-versions¶

    pisa update-versions [--out <dir>] [--only <name>[,<name>…]] [--check build|tests] [--dry-run]

    Keeps the versions of generated projects current without templates having to be updated by hand. For every library of the plan Pisa asks for the newest stable version (Spring: Maven Central, Hono: npm; pre-releases such as -rc, -beta, -M do not count) and shows what would change. Without --dry-run it writes the new versions into the versions { } of the architecture description (spec/*.adl; versions are there so that they are part of the spec), after a copy of the project has passed them: Pisa applies them to the copy (init --adl … --force and generate, as the recipe recorded them) and checks them:

    • without --check: init and generate must run through;
    • --check build: in addition mvn -q compile or npm install and npm run typecheck;
    • --check tests: in addition mvn -q test or npm install and npm test.

    If the check fails, Pisa tries the libraries one by one: what passes is taken over, what breaks stays at its version and is named with the end of the error output (exit code 1). The real project stays untouched until it passes. After that init --adl --force and generate run in the project, so pom.xml/package.json and the other bootstrap files follow, and both steps are in the recipe; replay matches.

    The versions then stay as they are until you call the command again (generate and replay deliver the same files); it is a kind of lock file, not "always the newest". --only prisma,hono restricts to single libraries (names as in the plan). Requirements and limits:

    • The project needs a spec/*.adl (init --adl), because the versions are in it; otherwise Pisa names the way.
    • init --force rewrites pom.xml, package.json and the other files written once (what you changed there by hand is lost; git diff shows it).
    • Needs the network; --check also needs mvn or node and npm and loads dependencies.
    • The Node.js types (typesNode) stay on the major version of the Node line; they are changed by hand.
    • The language model takes no part in this. If a new version breaks the project, the template has to be adjusted by hand (eject-templates); a repair step by the model is only planned.

    pisa extend¶

    pisa extend --specify "<wish>"
pisa extend --plan [--feature <NNN>] [--state]
pisa extend --implement [--feature <NNN>]
pisa extend --check [--feature <NNN>] [--skip-tests]

    Extends Pisa itself, spec-driven in the manner of GitHub Spec Kit, in four phases. It works only in a checkout of Pisa's own source repository, not in the installed binary. This command is meant for people who develop Pisa; you do not need it to use Pisa.

    Phase Spec Kit Pisa Model
    --specify "<wish>" constitution, specify, clarify the model writes spec.md (purpose, example, acceptance, rules, layers) through a checked tool, three attempts yes
    --plan plan, tasks plan.md with the tasks of the layers named in spec.md; --state appends them to the state file; an existing plan is not overwritten no
    --implement implement prints the assignment for the coding agent (constitution, spec, plan); Pisa writes no code no
    --check converge tests, type check, all tasks ticked, user guide and plan changed; "Converged" or the gaps, exit 1 no

    --specify is not a recipe step (the recipe belongs to generated projects). See pisa extend --help.

    pisa hash-password¶

    pisa hash-password [--stdin]

    Prints the bcrypt hash of a password for a user in security.yml (applications with authentication session, see 4g). Asks for the password twice without echo; --stdin reads it from standard input (printf '%s' "$PASSWORD" | pisa hash-password --stdin). There is no password as an argument. At least 8 characters, at most 72 bytes; the hash has a random salt (the same password gives a different, valid hash every time).

    pisa replay¶

    pisa replay --from <project> --out <new-dir>

    Rebuilds a project from its .pisa/recipe.json in an empty folder and checks every generated file against the recorded hash. See Recipe and replay.

    pisa mcp¶

    Starts an MCP server (stdio) for other MCP-capable agents, with two tools: generate (like pisa generate --file <model.dml> --out <dir>, for Spring projects after init) and parse_domain_model (the .dml as JSON). The model is always a .dml file.

    Called by hand the command seems to wait idly: a stdio MCP server reads JSON-RPC from stdin and writes answers to stdout, so stdout stays empty otherwise. The log (start message, one line per tool call) goes to stderr; Ctrl-C ends the server. To register it e.g. in Claude Code: claude mcp add pisa -- pisa mcp.

    Specs¶

    Domain model (.dml)¶

    type Zip = String ~ "[0-9]{4}"            // named type with a rule, defined once
enum Status { ACTIVE, SUSPENDED ("Blocked"), CLOSED }   // fixed values, optionally with a display text

@table("T_AUTHOR")                        // name of the table; derived if missing (author)
@operations(create, read, update)         // allows only this (no delete); if missing: everything (full CRUD)
entity Author {
    @id id: Long                          // exactly one @id per entity
    @column("C_NAME")                     // name of the column; derived if missing (name)
    name: String(1..80)                   // range: the length for String, the value for numbers
    status: Status                        // enum as a field type
    email: Email? unique                  // ? = optional (nullable), unique = unique
    oneToMany books: Book mappedBy author // other side of a relation
    oneToOne person: Person composed      // part (aggregate), see below
}
entity Book {
    @id id: Long
    title: String
    publishedAt: Date?
    manyToOne author: Author
}
    • Types: String, Int, Long, Double, BigDecimal, Boolean, Date, DateTime and the formats Email, Url, Phone (strings with a format). Depending on the target not all are generated; an unsupported type is rejected on generating, with the name of the target.
    • Rules on the type: Int(0..150), String(1..80), BigDecimal(0..), String(..2000): a range in parentheses, either bound may be missing; for String it is the length, for numbers the value (bounds inclusive). String ~ "[0-9]{4}": a pattern (regular expression), the whole value must match; write backslashes twice ("\\d{4}"). Email, Url, Phone have a built-in format and no pattern. type Zip = String ~ "[0-9]{4}" names a type together with its rules; the types of a folder apply to all its .dml files like the entities. A range on the field replaces the one of the named type as a whole. Required is the default (? makes a field optional), there is no keyword for it. The editor reports rules that do not fit (a range on Boolean/Date, a pattern on numbers, min > max, an invalid expression, a rule on a generated @id).
    • enum: enum Status { ACTIVE, SUSPENDED ("Blocked") } defines fixed values (at least one, UPPER_SNAKE_CASE, separated by commas; the text in parentheses is optional and is shown in the page instead of the name). An enum is a field type (status: Status, optional with ?, unique allowed) and applies like a type to all .dml files of the folder; names of enums, types and entities must not be duplicated. No range and no pattern on an enum field, and an enum is not an @id. The editor reports duplicate or invalid values. For every enum used Pisa generates model/Status.java, on the field @Enumerated(EnumType.STRING) (the name is in the database, never the ordinal), in the page a selection field (<select> with the values, display text if present; in the Salt mockup ^status^), and the tests take the first value (the second when changing); an unknown value is rejected with 400 (test answers400ForAnUnknownValueOf_status). In the style layered the DTO uses the same enum; therefore the layer dto may access model (ArchUnit). Not possible: values with fields of their own, an enum that no field uses (it is not generated), and the target prisma-hono-ink.
    • @operations: @operations(create, read, update) after @table and before entity names what may be done with the rows of the entity: create, read, update, delete. Without it everything is always allowed (full CRUD); Pisa never restricts by itself, and propose-model/propose-specs do not suggest it. read is required (lists and the selection fields of other entities need it, so there is no "write only"). The names are normal names, not keywords: a field read or an enum value DELETE stays possible; the editor reports unknown ones (Unknown operation 'x' (allowed: create, read, update, delete)), duplicate ones and a missing read. On a composed part the statement is an error (it is edited together with its root, that is where it belongs). Effect in both targets: the interface answers a disallowed operation with 405 (with an Allow header; with Spring without the method in the controller, with TypeScript via meta.operations); the page shows no delete button without delete, no edit button without update, no form for creating without create (with only update it appears only when editing; for viewing it always exists, see "Display mode" in 4g); in the table of another page "Open" leads without update only to the page. Repository and service stay complete. The generated tests check what is missing for 405 and create the rows they need directly through the repository where create is missing (with TypeScript also for the browser tests); the error cases when creating (required value, rules, uniqueness) are dropped without create. Not possible: other operations than these four (rights per user, single fields read-only).
    • @table and @column: @table("T_CUSTOMER") before entity sets the name of the table, @column("C_NAME") before a field (after @id if present: @id @column("ID") id: Long) that of the column; without it the derived name stays (table snake_case of the entity name, column the field name). Letters, digits and _ are allowed, not a digit at the start; tables of a folder and columns of an entity must be different (case-insensitive). The column of a relation cannot be named yet.
    • What Pisa makes of it (Spring): Bean Validation annotations on the entity (@ValidEmail, @Size, @Min/@Max, @DecimalMin/@DecimalMax, @Pattern, @Valid on parts), @Valid in the controller and spring-boot-starter-validation in the pom.xml. A violated value is answered with 400 and {"error": "...", "fields": {"email": "must be a well-formed email address"}}. Email is checked by Apache Commons Validator (foo@bar without a domain ending is invalid, unlike with Hibernate's @Email and type="email"); for this Pisa generates @ValidEmail in the package validation (only if the model has an Email field).
    • What the page does: The form checks itself before sending (novalidate, rules from the page configuration): required, length, range, pattern, and Email/Url with validator.js (WebJar org.webjars.npm:validator, property <validator.version>). A wrong field turns red (class invalid, message below it, disappears when typing), and nothing is sent. The same holds for the fields of a 400 answer from the server. In addition Pisa sets type="email"/url/tel, min/max, minlength/maxlength and pattern as attributes. For every rule Pisa generates a controller test (an invalid value is rejected with 400) and a UI test (marksTheFieldRedForAnInvalidValue, for Email with foo@bar), and per page a test with an intercepted 400 answer (marksTheFieldTheServerRejects). Valid example values Pisa derives from the rule; for a pattern from which they cannot be derived (e.g. lookarounds), generate aborts with the pattern in the message.
    • Relations: oneToOne, oneToMany, manyToOne, manyToMany. The owning side has the column; the other side carries mappedBy <field>.
    • composed: makes the target a part of the entity (aggregate). It is saved, edited and deleted with it and edited in the form of the root; fields are reached by path (address.street). Rules the editor checks: only oneToOne/oneToMany, never with mappedBy, exactly one owner, referenced nowhere else. Lists of parts (oneToMany … composed) do not work yet.
    • One folder = one model: all .dml in the same folder share the namespace; duplicate entity names are reported.
    • Editor support: IntelliJ plugin and VS Code extension (syntax, checking, class diagram domain-model.puml/.md, updated on saving). See Setting up editor and PlantUML.

    Forms: .ui.md with a Salt mockup¶

    A form description is free Markdown in spec/<entity>.ui.md — the only file for the form. The Salt mockup in it is the layout: generate reads it directly. You can draw it yourself or have it proposed from the prose (propose-layout). There is no locked copy or checksums; instead generate rejects a mockup that no longer matches the model.

    The layout knows: groups (with a heading), fields in order, rows (fields side by side), labels, tables (read-only, for other sides such as "books of an author") and texts (title, buttons). Which input element a field gets always follows from the type (text, number, checkbox, date, date+time; reference = selection, owning collection = multiple selection).

    The Salt mockup in short:

    In the mockup Effect
    {^"Heading" … } group with a heading
    Label \| "field" field with a label
    A \| "a" \| B \| "b" two fields in a row
    Country \| ^address.country^ relation (selection)
    [ ] booked Boolean (checkbox)
    row Books, then {# with Title \| ISBN and books.title \| books.isbn table of the other side
    title Author title of the page, the menu entry and the form
    [Save], [Save] \| [Cancel], [Create] \| [Save] \| [Cancel] button texts

    Every member of the form must appear exactly once. An unknown or duplicate name, a missing member or an element that does not fit the type is rejected with the line in the .ui.md, generate then writes nothing.

    propose-layout writes two marked sections at the end of the .ui.md (<!-- pisa:mockup --> with the proposed mockup, <!-- pisa:notes --> with wishes the layout cannot express); everything outside stays byte for byte as you wrote it. You may change the mockup between the markers; delete the two marker lines if it should belong to you (then no later run replaces it any more). A second mockup next to your own does not exist: exactly one is read. Files from older versions call the section pisa:preview; it applies the same.

    A part has no form of its own: you describe its fields in the .ui.md of the root, by path (person.address.zip in spec/author.ui.md).

    Use cases: .uc.md¶

    Markdown for humans (actor, goal, flow, PlantUML diagram). From it Pisa reads only the headings ## UC<n> <title> and two lines per use case (German or English label):

    ## UC1 Capture contact

- **Form:** Author
- **Test:** create
    • Form: / Formular: — link to the .ui.md; the file name determines the entity (author.ui.md → Author, a part such as Person leads to its root).
    • Test: — create | edit | delete (German: anlegen | ändern | löschen): the scenario in the browser.
    • Actor: / Akteur: — with login: if the actor is named like a role of the .adl (upper or lower case, then a name in parentheses may follow: USER (Secretariat)), the browser test runs as the test user of this role and with what the role sees on the page; if the role may not do the scenario (for example USER deletes a company that it may only read and change), generate refuses the use case with the reason and writes nothing. Another actor ("Secretariat") stays documentation. For roles as the actor propose-specs writes the role with the fewest rights that may do the scenario (on a tie the one named last, so USER); what no role may do, it does not propose.

    For every use case generate writes src/test/java/<package>/ui/UC1UiTest.java (Playwright, profile ui: mvn test -Pui) with @Tag("UC1") and @DisplayName("UC1 Capture contact"). Create fills in the form and saves, edit creates and edits, delete creates and deletes (values as in the page tests). Without a Test: line, with an unknown word or without a matching entity a @Disabled test is generated with the steps as a comment; generate reports the reason. The .uc.md is an input in the recipe.

    A disallowed operation is rejected: a use case is only a test, not a function of the application, and removes nothing from the application when you remove it (the old test file UC<n>… stays: Pisa never deletes). If it asks for something the entity does not allow in @operations (Test: delete with delete missing; edit needs update, create needs create; for a part the root counts), generate aborts and writes nothing: UC6 (spec/x.uc.md): Company doesn't allow "delete" (@operations(create, read, update)) but the test line says "delete". Then change @operations, change the Test: line or remove the use case.

    A contradiction is rejected: if the title names another scenario than the Test: line (e.g. "Delete contact" with Test: edit; recognized by words such as delete/löschen, change/ändern, capture/erfassen/create), generate aborts with a message and writes nothing. Titles without such a word (e.g. "Maintain countries") are free.

    Project spec (project.spec.json)¶

    Fields: target, groupId, artifactId, basePackage, javaVersion, database (today h2). pisa init writes them, later commands read and check them. Changing them by hand is allowed, but files already generated (package, pom.xml) do not change by themselves because of it.

    Customizing templates¶

    What init and generate write, Pisa renders from Nunjucks templates. The built-in templates can be overridden without rebuilding Pisa:

    pisa eject-templates --target spring-boot --out ./shop     # copies to ./shop/.pisa/templates/spring-boot/
# e.g. edit .pisa/templates/spring-boot/static/app.css.njk, then:
pisa generate --file spec/shop.dml --out ./shop
    • Pisa takes <out>/.pisa/templates/<target>/ automatically, or a folder via --templates <dir>.
    • Only files that are there override the default; if you delete one, the built-in one applies again.
    • Pisa reports which modified templates it uses ("Info: using N modified template(s) …") and which unchanged copies are lying around (delete them so that future defaults apply).
    • A broken template stops the run before anything is written.
    • Paths and package names of the generated files are in Pisa's code, a template cannot move a file.
    • Stumbling block: after a block tag ({% endfor %}) the line break is swallowed; end the file with text if you need a line break at the end.

    Recipe and replay¶

    Every command that writes into a project (init, generate, eject-templates, propose-layout, propose-architecture, propose-model) is recorded as a step:

    • .pisa/recipe.json: machine-readable (arguments, inputs, templates used, outputs with SHA-256).
    • README.md: a section "How this project was created" between <!-- pisa:recipe:begin --> and <!-- pisa:recipe:end -->. Text outside belongs to you. A foreign README without markers stays untouched, the section then lands in .pisa/steps.md.

    Steps can be repeated from the project folder (--out ., relative paths, resolved options, no timestamps). An identical second run adds nothing ("Recipe unchanged").

    pisa replay --from ./shop --out ./shop-copy runs the steps one after the other as separate pisa calls and finally checks all files against the hashes. Steps with an LLM (propose-layout) are not run again, their outputs (the .ui.md) are copied. A mockup you drew yourself needs no step: generate has the .ui.md as an input. A deviation, a missing file or a failed step is listed, exit 1.

    Limits: manual changes to generated files are not recorded (they belong in version control anyway); paths outside the project are used as they are, with a warning.

    Recommendation: put spec/, .pisa/, project.spec.json and README.md into Git; not target/.

    Not yet possible¶

    So that none of this is expected (as of 0.13.0):

    • Lists of parts (oneToMany … composed).
    • Schema migrations (Flyway): Hibernate manages the schema; switching the database H2 ↔ PostgreSQL goes through the architecture plan (section 4c).
    • Generating the specs from requirements (requirements.md → architecture → model) in one step. Singly it works, both proposals read spec/requirements.md (since 0.10.0) if there is no description of their own: the model can be proposed by an LLM (propose-model), the architecture too (propose-architecture), forms and use cases can be derived from the model (propose-specs, without an LLM). The proposals are tested automatically only against a fake model; with a real model there was one run by hand each.
    • The architecture description .adl knows only one backend with one database; several containers, gateway, broker, hexagonal and assigning entities to backends are missing. A changed .adl needs init --adl … --force.
    • Pages: the display mode (click on a row) follows the rights alone; it cannot be switched on or off in the specs and no view form of its own (<entity>.view.md) can be described (today only through your own page templates).
    • pisa play: steps in which a file is changed by hand (7a, step 8 of the tutorials) and browser steps stay manual; the text "You should see" is not checked (only exit codes); with --llm it has never been run with the tutorials.
    • pisa update-versions: only libraries that Pisa can look up (Spring: Maven Central, Hono: npm; Docker tags such as postgres and the Node line not); if a new version breaks the project it stays out, Pisa does not adjust a template itself. Checked by hand with real projects (Hono: library-hono, TypeScript 7.0.2, all 122 tests; Spring: library-spring, --check build, after which replay matches and a second run finds nothing newer). That a version breaks the check and stays behind is shown only by unit tests.
    • docker: one image per project, only Dockerfile and Compose; Testcontainers tests only with Spring and PostgreSQL (Hono: the tests run against the compose database, no Testcontainers); no image build in the CI file (ci.yml), no push to a registry, no multi-architecture images, no health check in the Dockerfile itself (only that of db in the compose.yml), no CD; port 8080 and /data are fixed.
    • deploy: only Render (free web service, releases only through the deploy hook); no Cloud Run, no database at Render, no domain of its own, no health check test after the deploy; not checked on a real account.
    • pipeline and scm: only GitHub (ci github, release github, host github), no other Git hosts (GitLab, Bitbucket, Codeberg); the workflows and templates are checked only to the extent that Pisa writes them and the files are valid YAML, not on a real GitHub run (tag, release, issue forms); no CD (deployment to the cloud); no command that creates the repository on GitHub (only the commands by hand in section 4e).
    • pisa extend: --implement prints only the assignment (a run with write access of the model to the paths of the plan is not built); --check does not check snapshots individually (they run in bun test) and no replay; the layer checklist is maintained by hand.
    • Deleting orphaned files; sorting, searching and number formatting on the pages.
    • The other side of a relation (mappedBy) cannot be set through the API.
    • Tests: none for composed lists, no test of the effect of the layout (groups, rows) in the browser; the tests of the relations set only one row of the other side (no error cases).
    • Login (authentication session): no user management in the browser, no password reset by e-mail, no token (JWT), no external providers, no HTTPS, no limit on login attempts, no rights per field or row.
    • Other targets (Quarkus and others); the target prisma-hono-ink does not know composed. The target hono-prisma (section 4f) does not know manyToMany, oneToMany without mappedBy and oneToOne without composed and has only 32-bit ids.
    • propose-architecture can propose runtime hono (only if the description mentions TypeScript or Node.js), without versions, and authentication session (only if it mentions login, users or roles); it does not propose the roles and users, init writes those as security.yml. With a real model neither has run yet (tested only with the tool directly).
