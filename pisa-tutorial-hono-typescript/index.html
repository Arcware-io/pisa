    Tutorial: from a description to a running application (TypeScript, Hono)¶

    You build a small address book (people with an address and a company) from scratch. You write only prose; an LLM proposes the architecture and the domain model, Pisa checks the proposals and generates a working TypeScript project (Node.js, Hono, Prisma) from them. After every step it says what you should see.

    As of pisa 0.13.0. Commands in detail: User Guide. Duration: about an hour, npm install downloads dependencies.

    Steps 2 and 4 call an LLM (two short calls); all other steps run without one. Without an LLM you write the two files yourself, as they are shown in the steps. At the end there are optional steps (10, CI with GitHub Actions; 11, Docker; 12, the cloud); pisa play --fast leaves them out.

    0. Requirements¶

    What Check
    Pisa 0.13.0 pisa --version shows pisa 0.13.0. Otherwise install it: User Guide, section "Installing Pisa" (curl, PowerShell or brew, no login)
    Node.js 24 or newer and npm node -v, npm -v. Node.js runs TypeScript directly, there is no build step
    LLM access for pi pi is set up with a model (see the pi documentation); needed only for steps 2 and 4
    Optional: Chromium for the browser tests npx playwright install chromium (step 7)
    Optional: Pisa plugin IntelliJ or VS Code colors .dml/.adl and shows errors while you write (User Guide, "Setting up editor and PlantUML")

    1. Create a folder and prepare Pisa¶

    mkdir adressen-hono && cd adressen-hono
pisa init

    You should see: Prepared .: doc/ (the user guide and both tutorials) and spec/. and the hint which tutorial you can read. pisa init without arguments creates no project yet, only what is the same for every kind of application: the folder doc/ with the user guide and both tutorials (Spring Boot and Hono) and an empty folder spec/. Which kind of application you want (Java with Spring Boot or TypeScript with Hono) you decide now, from the tutorials and the description in step 2; a project is created only in step 3. All further commands run in this folder.

    2. Describe the architecture and have it proposed¶

    pisa propose-architecture --out .

    You should see: Created spec/architecture.md with a starting text - describe the architecture there, …. Open spec/architecture.md, delete the line <!-- pisa:starting-text --> and replace the text with something like this. Two places decide that it becomes TypeScript: the technology (TypeScript, Hono) and the embedded database (with TypeScript that is SQLite):

    # Architecture

Management of people with their address and the companies they work for. It is a
prototype for a demo, the data does not have to survive a restart.

- Style: The code should be layered (controller, service, repository), with DTOs between
  controller and service.
- Database: embedded (SQLite), no separate server.
- Technology: TypeScript on Node.js with Hono, web UI with Alpine.js, served by the backend.
- Docker: The application should also be buildable as a Docker image (only the image, nothing more).
- Login: Users sign in with name and password, there are roles.
  Admin for the administration, has more rights, can e.g. create companies.
  User for normal users, who can read or change companies, but not create or delete them.
- Versions: no special requirements, the newest stable ones are fine.

    Then once more:

    pisa propose-architecture --out .

    You should see: the streaming text of the model, at the end Architecture proposal complete: spec/architecture.adl and the line Create the project from it: pisa init … --out . --adl ….

    Open spec/architecture.adl and check it:

    architecture AdressenHono {
    container db : database { engine sqlite }
    container api : backend {
        runtime hono
        authentication session
        roles {
            ADMIN
            USER {
                Company: read, update
            }
        }
        uses db
        components layered
    }
    container web : frontend { technology alpine  servedBy api }
    docker { }
}

    (The file is formatted over several lines; comments at the top name what the model could not cover.) If something is wrong, change the file by hand: it is yours from now on.

    The line runtime hono decides that a TypeScript project is created; a package and versions do not belong to it (those are Java things). The line authentication session (login with users and roles, step 7b) comes from the sentence "Login" in your description. The roles from the description are in the roles block of the .adl: ADMIN without a block may do everything, USER may only read and change companies (Company: read, update), everything else as before. From it init writes the security.yml (step 7b), and generate generates the tests per role. If one of these statements is missing in your file (a model does not always do what the description says), write it by hand into the api container. engine sqlite exists only with runtime hono; postgresql works too.

    The empty block docker { } (from the sentence "Docker" in your description) makes init write a Dockerfile and a .dockerignore, nothing more. You do not have to use them; how to try them is in the optional step 11. If the block is missing in your file, write docker { } by hand before the last bracket, or leave it out if you need no image.

    If it does not work: "ended without an accepted architecture" means the model answered invalidly three times, or not at all through the tool; formulate the description more precisely and repeat. With an existing .adl the command does nothing, except with --force.

    3. Create the project¶

    pisa init --out . --artifact adressen-hono --adl spec/architecture.adl

    You should see: Architecture from spec/architecture.adl: style layered, database sqlite. and the list of files (package.json, tsconfig.json, prisma.config.ts, src/db.ts, src/index.ts, application.yml, …, .pisa/architecture.plan.json, Dockerfile, .dockerignore). New are also spec/README.md (a guide to the specs) and README.md with the recipe of the project. doc/ from step 1 stays as it is. You do not need a --target: Pisa takes the target from runtime hono.

    4. Describe the domain model and have it proposed¶

    pisa propose-model --out .

    You should see: Created spec/domain-spec.md with a starting text - describe the domain model there, …. In spec/domain-spec.md delete the marker line again and write:

    # Domain model

A simple address book for a small office. It stores people with
their address and the companies they work for.

- **Person:** First name and last name are required (at most 80 characters each). The
  e-mail address is optional and may occur only once. Phone and
  birthday are optional. Every person has a status: active, blocked
  (displayed "Blocked") or archived.
- **Address:** Street and city are required, the postal code consists of exactly
  4 digits. The address belongs firmly to one person (a part), it has
  no page of its own and is saved and deleted with the person.
- **Company:** The name is required and unique. A company has many people,
  a person works for at most one company.

Not wanted: history of the addresses, access rights.

    pisa propose-model --out .

    You should see: Model proposal complete: spec/adressen-hono.dml (the file name is the project name) and the line Check it, then: pisa generate --file spec/adressen-hono.dml --out ..

    Check spec/adressen-hono.dml closely, this is the most important step: Are all three entities there? Does Person have a status as an enum, Address the rule for the postal code (~ "[0-9]{4}"), address on the person as composed, employees on the company as mappedBy company? Wishes that the language does not express (here: history, rights) stand as // Not covered: … above the first line. The model is a proposal, not the truth: change by hand what is not right; the plugin shows errors while you write. For comparison, this is what a fitting model looks like:

    enum PersonStatus { ACTIVE ("Active"), BLOCKED ("Blocked"), ARCHIVED ("Archived") }

type Plz = String ~ "[0-9]{4}"

entity Person {
    @id id: Long
    firstName: String(1..80)
    lastName: String(1..80)
    email: Email? unique
    phone: Phone?
    birthday: Date?
    status: PersonStatus
    oneToOne address: Address composed
    manyToOne company: Company
}

entity Address {
    @id id: Long
    street: String
    zip: Plz
    city: String
}

entity Company {
    @id id: Long
    name: String unique
    oneToMany employees: Person mappedBy company
}

    The relations must be those the TypeScript target can do: manyToOne, oneToMany … mappedBy and oneToOne … composed. manyToMany, oneToMany without mappedBy and oneToOne without composed are rejected by Pisa with not supported by this target yet.

    5. Derive forms and use cases (without an LLM)¶

    pisa propose-specs --out .

    You should see: Wrote spec/person.ui.md, Wrote spec/company.ui.md, Wrote spec/use-cases.uc.md. You can adjust the forms (.ui.md, with a Salt mockup as the layout) and the use cases (one browser test each) later; the command never overwrites existing files. With a login with roles it writes as the actor of every use case the role with the fewest rights that may do it (creating and deleting companies: ADMIN; changing companies and everything on people: USER), and generate lets the browser test run as that role.

    6. Generate code¶

    pisa generate --file spec/adressen-hono.dml --out .

    You should see: Generated hono-prisma files for Person, Address, Company: and the list of generated files (models, repositories, services, DTOs, routes, pages, tests) and at the end Recorded step N in .pisa/recipe.json and README.md.

    File Content
    prisma/schema.prisma the database schema (both sides of every relation, enum, table names)
    src/model/<Entity>.ts the type of the JSON and the metadata of the entity (rules of the fields)
    src/repository, src/service, src/dto, src/mapper, src/route data access, service, DTO, mapper and REST interface (only for entities with a page of their own: Address is a part of the person and has none)
    public/*.html, app.js, app.css the pages (Alpine.js)
    src/lib/* the runtime: checking the rules, conversion, pages, login, error answers
    test/api/*.test.ts, test/architecture.test.ts API tests, tests per role and the layer test
    test/ui/*.spec.ts browser tests (Playwright), per page, menu and use case

    7. Start and try it out¶

    npm install

    Then you start the server:

    npm start

    npm start generates the Prisma client and the tables (prisma generate, prisma db push) and starts the server. You should see: adressen-hono is running on http://localhost:8080.

    Open http://localhost:8080/ in the browser, through the running server (not the files from public/ directly: Alpine.js and the scripts come from the server, in the file itself buttons and texts are empty): a menu with People and Companies. The heading of the start page is "AdressenHono", the name from architecture AdressenHono { in the .adl; it is app.title in application.yml (change it, restart the application). The application redirects to the login page: sign in with admin / admin and choose a new password on the "Change password" page (twice, at least 8 characters); who is signed in is shown in the hamburger menu (☰) at the top right. Roles and more users: step 7b. Create a company, then a person with an address and choose the company. A click on a row of the list shows the entry read-only (display mode); whoever may change it has "Edit" there. Try the rules: a postal code with 3 digits, the same e-mail twice, an empty last name; the field turns red and the server answers 400 with the message per field (for example with curl and the session of your login; without it it answers 401):

    {"error":"Some values are not valid.","fields":{"address.zip":"must match \"[0-9]{4}\""}}

    The data is in the SQLite file adressen-hono.db in the project folder (open it with any SQLite tool). End with Ctrl+C.

    npm test                                          # API tests, tests per role, layer test

    And the browser tests (install Chromium once):

    npx playwright install chromium                   # once
npm run test:ui                                   # browser tests

    You should see: ℹ pass 59, ℹ fail 0 and 22 passed. (bun test works too: it starts npm test; Bun itself cannot load the SQLite driver.) Every test run takes a fresh database in a temporary folder; your adressen-hono.db stays untouched. The layer test (test/architecture.test.ts) checks the imports in src/: route → service → repository, and only src/db.ts knows Prisma.

    7a. Optional: restrict operations (@operations)¶

    Every entity allows all four operations by default (create, read, change, delete). Whoever wants to block something writes it into the model, with @operations before entity. Example: companies should be created, read and changed, but not deleted. Add to spec/adressen-hono.dml:

    @operations(create, read, update)
entity Company {
    …
}

    read must always be included (lists and selection fields need it). Without the line everything is allowed; Pisa never blocks anything by itself. Then:

    pisa generate --file spec/adressen-hono.dml --out .

    You should see: an abort, nothing is written:

    UC6 (spec/use-cases.uc.md): Company doesn't allow "delete" (@operations(create, read, update)) but the test line says "delete"
Nothing was written. Allow the operation in @operations of the entity or give the role the right in `roles` of the .adl (then `pisa init … --force` and delete security.yml), or change the Test: line or the Actor:, or delete the use case.

    This is intended: the use case "Delete company" (UC6) asks for something the company no longer allows, a contradiction between two specs. Three ways out: allow delete again, change the Test: line, or (here) drop the use case. In spec/use-cases.uc.md delete the section ## UC6 … and in the PlantUML diagram the two lines with UC6, then run pisa generate again. Pisa never deletes files: the old browser test of the use case stays and would fail, delete it by hand (generate names it under Info: browser tests of use cases that are no longer in spec/*.uc.md): test/ui/UC6.spec.ts.

    Restart the application (npm start) and check:

    • The "Companies" page has no delete button any more; creating and changing still work.
    • The interface blocks deleting as well: curl -i -X DELETE http://localhost:8080/api/companies/1 answers 405 (Method Not Allowed) with an Allow header, the company stays (GET still gives 200). People can still be deleted.
    • npm test checks this for you: the generated test answers 405 for a delete expects 405, and the "delete" test of the company is dropped.

    More about this (names, error messages, effect in both targets, interplay with roles): User Guide, section "Domain model (.dml)", @operations. Change the line to @operations(create, read, update, delete) or delete it if you want to lift the restriction again.

    7b. Rights and users¶

    You already switched the login on with the line authentication session in the .adl (details: User Guide, section 4g). For it init wrote security.yml (roles and users), login.html and change-password.html, generate the login files (src/lib/security.ts, test/api/security.test.ts, test/api/roles.test.ts). The .dml and the mockups know no roles: they are not in the domain model. If you write the line only later, init … --force and generate are needed afterwards.

    • Sign in with admin / admin (if you have not yet): the "Change password" page appears, where you enter the new password twice (at least 8 characters, not the user name). After that ADMIN may do everything the model allows: not even he deletes companies if you did 7a (the rights of a role intersected with @operations). Who is signed in is shown in the hamburger menu (☰) at the top right, with "Change password" and "Sign out".
    • Sign out and sign in as user / user (choose a new password again): USER may edit people fully, companies only read and change (block roles, see below). A write access through curl without login answers 401; signed in but without the right, 403.

    Rights for this example: They are already in the .adl (block roles, step 2) and thereby in security.yml: USER edits people (with their address) fully, companies he may only read and change (so it says in the description of the architecture). init wrote the file from the block:

      USER:
    "*": [create, read, update, delete]
    "Company": [read, update]            # the list of an entity replaces "*"

    Sign in as user: the "Companies" page has no buttons for creating and deleting any more (changing works), and a curl POST or DELETE on /api/companies answers 403. You can still edit people. A click on a company shows it read-only, with "Edit" for changing; whoever could only read would have no "Edit" there. You can change the rights in two ways: by hand in security.yml (restart the application, no generate), or permanently in the roles block of the .adl (then delete security.yml, init … --adl … --force and generate). The tests and the use cases follow the .adl: test/api/roles.test.ts checks for every role and every entity what is allowed (not 403) and what is not (403), and the use cases with **Actor:** USER or ADMIN (step 5) run in the browser as that role.

    About passwords: a user's start password is his name (admin/admin, user/user); there is no password in security.yml. The new password is never in plain text, the hash ends up in the table usr_password of the application's database; the application never changes security.yml. With SQLite the password stays in the file, with PostgreSQL in the database. Deleting a row of the table resets the user to the start password.

    Your own roles and users: enter them in security.yml (the hash comes from pisa hash-password, which asks for the password twice without echo) and restart the application; no generate is needed. admin/admin and user/user are publicly known, for development only.

    npm test signs in in the generated tests as test users (they are in test/security-test.yml, not in your security.yml) and additionally checks 401, 403 and setting the password (test/api/security.test.ts).

    8. Carry through a change¶

    Change the description, not the code. Two ways:

    • By hand in the model: add a field in spec/adressen-hono.dml, say title: String(..40)? on Person. The form must know it too: spec/person.ui.md is a layout in which every field occurs exactly once; add a row to the mockup, say Title | "title" below the last name. Then pisa generate --file spec/adressen-hono.dml --out . and npm test. The code, the pages and the tests follow. Without the mockup row generate aborts and writes nothing: The Salt mockup in spec/person.ui.md can't be used: … missing "title". (Alternatively delete spec/person.ui.md and run pisa propose-specs --out . again: the default mockup contains all fields.)
    • Have it proposed anew: change domain-spec.md and pisa propose-model --out . --force (overwrites spec/adressen-hono.dml, so your manual changes there).

    9. Reproduce¶

    cd ..
pisa replay --from adressen-hono --out adressen-hono-copy

    You should see: … All N generated file(s) match the hashes recorded in the recipe. Pisa runs the recorded steps (init, generate) again in a new folder and compares files with the checksums in the recipe (adressen-hono/.pisa/recipe.json). The LLM steps are not repeated: their result (spec/architecture.adl, spec/adressen-hono.dml) is copied from the source project.

    10. Optional: build and test on every push (CI)¶

    This is an extra; you need it for nothing else. If GitHub should build the project on every push and run the tests (GitHub Actions), add the pipeline block to spec/architecture.adl before the last bracket and apply the .adl again:

        pipeline {
        ci github
    }

    The commands do both instead of you (replace the last line of the .adl, then init --force). Run the whole block: pisa init … --force alone changes nothing as long as the pipeline block is not in spec/architecture.adl, and without it Pisa creates neither a repository nor a commit.

    cd adressen-hono
sed -i.bak '$ d' spec/architecture.adl && rm spec/architecture.adl.bak
printf '    pipeline {\n        ci github\n    }\n}\n' >> spec/architecture.adl
pisa init --out . --artifact adressen-hono --adl spec/architecture.adl --force

    You should see: the new file .github/workflows/ci.yml in the list and Git repository created, first commit made (branch main …). Pisa creates the repository and makes the first commit (Initial project (pisa init)), local only; it does not know your GitHub account, you take care of that. There are three cases, one paragraph each:

    Normal case: Pisa made the commit. Then you create the repository on GitHub and upload it (needs the GitHub CLI gh, once gh auth login):

    gh repo create adressen-hono --private --source . --push

    Pisa made no repository or no commit. These are the four cases:

    • The pipeline block is missing in spec/architecture.adl (only the last line was run): neither repository nor commit.
    • pisa play --fast left out the whole step: neither repository nor commit.
    • The folder is already in a Git repository: Pisa does not touch it, it makes no commit.
    • Name and e-mail are missing in your Git configuration: the repository is there, but no commit.

    git status in the project folder shows it: "not a git repository" means there is none. Then you make the repository and the commit yourself and go on afterwards as in the normal case (git init does no harm if the repository is already there):

    git init -b main
git add -A
git commit -m "Initial project"

    Without gh. Create an empty repository on github.com and connect it to your folder (instead of gh repo create):

    git remote add origin git@github.com:<your-name>/adressen-hono.git
git push -u origin main

    After that the pipeline runs on GitHub (tab "Actions"): the job tests and the job browser-tests. The file is yours, even init --force does not overwrite it. Pisa has not yet checked it on a real GitHub run; if a job turns red, that is a finding for Pisa. More about it: User Guide, section 4e (pipeline). pisa play --fast leaves this step out.

    11. Optional: try it with Docker and the real database¶

    This is an extra as well. So far everything runs on SQLite in a file. The Dockerfile from step 3 is already there; with Docker you can build the application as an image and run it against a real PostgreSQL, much like later in the cloud. You need it for nothing else. pisa play never plays this step (everything skip, even without --fast): try it by hand. Requirement: Docker is running (docker version), ports 8080 and 5432 are free.

    1. Only the image, with a port. The Dockerfile builds the application as an image. A Dockerfile does not publish a port by itself (EXPOSE is only a hint), so -p 8080:8080 belongs in the command, otherwise you cannot reach the application from outside (in IntelliJ: set "Bind ports" in the run configuration):

    docker build -t adressen-hono .
docker run --rm --name adressen-hono -p 8080:8080 -v adressen-hono-data:/data adressen-hono

    You should see: the application at http://localhost:8080/login.html (SQLite in the container; users admin/admin and user/user, the chosen password is in the SQLite file in the volume adressen-hono-data and stays). Stop with Ctrl-C.

    2. Switch to PostgreSQL. In spec/architecture.adl replace the line engine sqlite by engine postgresql, apply the .adl again and generate the code again (generate rewrites the Prisma schema). With PostgreSQL Pisa writes the compose.yml with the application (app) and the database (db) even without the line compose in the docker block.

    sed -i.bak 's/engine sqlite/engine postgresql/' spec/architecture.adl && rm spec/architecture.adl.bak
pisa init --out . --artifact adressen-hono --adl spec/architecture.adl --force
pisa generate --file spec/adressen-hono.dml --out .

    3. Start the application and the database.

    docker compose up --build

    You should see: the image is built (one to two minutes the first time), then adressen-hono is running on http://localhost:8080. Open http://localhost:8080/login.html (users admin/admin and user/user; the chosen password is in the table usr_password of PostgreSQL and stays). Stop with Ctrl-C, clean up with docker compose down (with -v also the data).

    4. Only the database (for developing and testing). docker compose up -d db starts only PostgreSQL; npm start and the tests take it (the address is in the plan, TEST_DATABASE_URL sets another):

    docker compose up -d db
npm test

    You should see: the same tests as in step 7, now against PostgreSQL (ℹ pass 59, ℹ fail 0). Afterwards docker compose down.

    If it does not work:

    • port is already allocated: another PostgreSQL or another application uses 5432 or 8080. Set other ports in the compose.yml ("5433:5432") or set database.port in .pisa/architecture.plan.json and apply the .adl again.
    • docker compose hangs at docker-credential-desktop: Docker Desktop's credential helper does not answer. Restart Docker Desktop or use a DOCKER_CONFIG without credsStore.
    • npm test says the database is not reachable: docker compose up -d db needs a few seconds until PostgreSQL is ready.

    12. Optional: into the cloud (Render)¶

    This is an extra as well and needs a GitHub repository (step 10) and an account at Render. Render runs the application's Docker image on a free web service: it sleeps after 15 minutes without requests (waking up takes about a minute) and has no persistent disk, SQLite and the chosen passwords are gone after every restart. Render's free PostgreSQL expires after 30 days: if you did step 11, set engine postgresql in spec/architecture.adl back to engine sqlite. pisa play never plays this step (everything skip).

    1. The lines in the .adl. The pipeline block (step 10) gets release github and deploy render; deploy needs the docker block, which you already have (step 2). If you skipped step 10, write the whole block before the last bracket:

        pipeline {
        ci github
        release github
        deploy render
    }

    Then apply the .adl again (render.yml and .github/workflows/cd.yml are created, once, after that they are yours):

    pisa init --out . --artifact adressen-hono --adl spec/architecture.adl --force

    You should see: render.yml and .github/workflows/cd.yml in the list and Deploy to Render: the comments at the top of render.yml say how.

    2. Set up at Render (in the browser). Push the project to GitHub (step 10). On dashboard.render.com New ▸ Blueprint, pick the repository and enter render.yml in the field Blueprint Path (Render looks for render.yaml by default). Then in the service Settings ▸ Deploy Hook copy the URL and save it in the GitHub repository under Settings ▸ Secrets and variables ▸ Actions as the secret RENDER_DEPLOY_HOOK_URL. The URL is secret: never write it into a file.

    3. Deploy. Only the deploy hook deploys, so only a tag v* (the release workflow creates the release, cd.yml calls the hook):

    git add -A && git commit -m "Deploy to Render"
git tag v0.1.0
git push origin main v0.1.0

    You should see: in the repository under Actions the run Deploy, at Render a new deploy and after a few minutes the application at the address of the service (https://<name>.onrender.com/login.html). The first access after sleeping takes about a minute. More about it: User Guide, section 4e ("Cloud: Render"). Pisa has not yet checked this on a real Render account: whether the service accepts the healthCheckPath is unchecked.

    You write prose and check proposals; the specs (.adl, .dml, .ui.md, .uc.md) are the source of truth, the code is derivable from them. The same specs give a Java project with runtime spring: see the Spring Java tutorial.

    Limits of the TypeScript target (as of now): no manyToMany, oneToMany without mappedBy and oneToOne without composed; ids are always 32-bit Int; engine sqlite is the embedded database; PostgreSQL (engine postgresql, with compose.yml, docker compose up -d) ran on 2026-10-21 against postgres:17.
