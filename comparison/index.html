    Comparison: Pisa vs. Spec-Driven Development Tools¶

    As of 2026-10-23.

    A comparison of Pisa (DSDD) with the most common spec-driven development approaches. The ratings are the author's own assessment, not a benchmark; star counts and vendor facts were taken from public pages at the time and were not re-verified later.

    Tools compared¶

    Tool Vendor Approach Stars (GitHub)
    Pisa CAS thesis prototype Domain & Spec Driven Development (DSDD): DSLs for the domain model and the architecture, deterministic generation, LLM only for proposals —
    GitHub Spec Kit GitHub/Microsoft Toolkit for the SDD workflow, agent-agnostic, specs as Markdown ~143k
    OpenSpec Fission-AI (YC) Lightweight spec framework, "agree first, then build", iterative ~73k
    AIUP AI Unified Process Requirements first, use cases at the center, Claude Code plugins ~100
    Kiro AWS Full IDE with SDD, Amazon Bedrock, requirements → design → code — (commercial)
    BMad Open source Agile AI-driven development, skills for Claude Code/Cursor ~2k
    JHipster Open source Established generator with JDL (JHipster Domain Language) ~21k

    Detailed rating by criterion¶

    1. Determinism (reproducibility of code generation)¶

    Tool Rating Reason
    Pisa ★★★★★ The skeleton generator is 100% deterministic; an LLM only for the propose-* commands, never for the final code generation
    JHipster ★★★★★ Template-based, no LLM in the generation
    AIUP ★★★☆☆ Specs steer the generation, but LLM variance in the implementation
    Spec Kit ★★☆☆☆ Specs are guardrails, the code is written by the agent (LLM variance)
    OpenSpec ★★☆☆☆ Similar to Spec Kit: specs plan, the agent implements
    Kiro ★★☆☆☆ The agent generates code based on specs
    BMad ★★☆☆☆ Agent-based implementation

    Pisa's advantage: The only tool (besides JHipster) that guarantees identical output for identical input. LLM hallucination is excluded structurally, not just restricted by a prompt.

    2. DSL / spec language¶

    Tool Rating Reason
    Pisa ★★★★★ Two typed DSLs: .dml (domain model with validators) and .adl (architecture); LSP with autocomplete, hover, diagnostics
    JHipster ★★★★☆ JDL (JHipster Domain Language) with its own parser, established
    AIUP ★★★★☆ Structured use case specs in Markdown with defined sections
    Spec Kit ★★★☆☆ Markdown-based, flexible but less structured
    OpenSpec ★★★☆☆ YAML/Markdown specs, lightweight
    Kiro ★★★☆☆ EARS notation for requirements, otherwise free text
    BMad ★★★☆☆ Markdown artifacts (brief, PRD, spec)

    Pisa's advantage: A real DSL with a language server, not just structured Markdown. Errors are found while typing, not only when generating.

    3. Schema validation (specs against the domain model)¶

    Tool Rating Reason
    Pisa ★★★★★ Core DSDD principle: specs are validated dynamically against the domain model (e.g. field names in .ui.md must exist in the entity)
    JHipster ★★★★☆ JDL validation, but less dynamic
    AIUP ★★★☆☆ Use cases reference entities, but manual consistency checking
    OpenSpec ★★★☆☆ Structure validation, but no domain model reference
    Spec Kit ★★☆☆☆ Specs are prose, consistency is the agent's responsibility
    Kiro ★★☆☆☆ Requirements validation, but no schema enforcement
    BMad ★★☆☆☆ Artifact structure, but no cross-validation

    Pisa's advantage: Hallucination is prevented structurally — an invented field name fails schema validation before code is generated.

    4. Target platforms¶

    Tool Rating Reason
    Spec Kit ★★★★★ Agent-agnostic: every platform the agent supports
    OpenSpec ★★★★★ Also agent-agnostic
    Kiro ★★★★★ AWS ecosystem, but flexible
    BMad ★★★★★ Agent-based, no restriction
    JHipster ★★★★☆ Spring Boot, Micronaut, Quarkus + Angular/React/Vue
    AIUP ★★★☆☆ Focus on Java/Vaadin, extensible
    Pisa ★★★☆☆ Spring Boot (Java) and Hono-Prisma (TypeScript); more targets possible but not built

    Pisa's disadvantage: A deliberately limited scope (a thesis prototype). The architecture allows more targets, but only two are implemented.

    5. IDE integration¶

    Tool Rating Reason
    Kiro ★★★★★ Its own IDE (a VS Code fork) with native integration
    Pisa ★★★★☆ VS Code and IntelliJ plugins with LSP (syntax, autocomplete, diagnostics, go to definition)
    AIUP ★★★★☆ Navigator plugin for IntelliJ/VS Code (test ↔ use case)
    Spec Kit ★★★☆☆ CLI + agent integration, no IDE plugin of its own
    JHipster ★★★☆☆ JDL Studio (web), various community plugins
    BMad ★★☆☆☆ Slash commands in Claude Code/Cursor
    OpenSpec ★★☆☆☆ CLI + slash commands

    Pisa's advantage: A real language server with all LSP features, not just syntax highlighting.

    6. Test generation¶

    Tool Rating Reason
    Pisa ★★★★★ API tests, layer tests, browser tests, one browser test per use case; tests per role
    JHipster ★★★★☆ Unit and integration tests, but less related to use cases
    AIUP ★★★★☆ Tests generated from use case specs, traceability
    Kiro ★★★★☆ Test generation is part of the workflow
    Spec Kit ★★☆☆☆ The agent writes tests, but not guaranteed to be structured
    BMad ★★☆☆☆ Agent-based
    OpenSpec ★☆☆☆☆ No focus on test generation

    Pisa's advantage: Tests are first-class output, not a by-product. Every use case automatically gets a browser test.

    7. UI generation¶

    Tool Rating Reason
    JHipster ★★★★★ Complete Angular/React/Vue frontends
    Pisa ★★★★☆ Alpine.js pages from .ui.md (Salt mockups), forms, lists, CRUD
    AIUP ★★★☆☆ Vaadin UI from specs
    Kiro ★★★☆☆ Agent-generated UIs
    Spec Kit ★☆☆☆☆ No UI focus
    OpenSpec ★☆☆☆☆ No UI focus
    BMad ★☆☆☆☆ No UI focus

    Pisa's approach: Lightweight Alpine.js UIs from Salt mockups (.ui.md). Not as comprehensive as JHipster, but deterministic and derived from specs.

    8. Agent-agnosticism¶

    Tool Rating Reason
    Spec Kit ★★★★★ 30+ agents supported (Claude Code, Copilot, Cursor, Pi, etc.)
    OpenSpec ★★★★★ Agent-agnostic by design
    BMad ★★★★☆ Claude Code, Cursor, extensible
    AIUP ★★★☆☆ Claude Code plugins, other agents via a marketplace
    Pisa ★★☆☆☆ Its own generator; an MCP server for external agents exists, but the focus is standalone
    Kiro ★☆☆☆☆ Its own IDE, no external agent support
    JHipster — No agent concept (a classic generator)

    Pisa's limitation: Pisa is primarily a generator, not an agent framework. The MCP server exists, but the main way is the CLI.

    9. Learning curve¶

    Tool Rating Reason
    OpenSpec ★★★★★ Minimalist, "5 concepts on one page"
    Spec Kit ★★★★☆ Good documentation, a clear 4-phase process
    Kiro ★★★★☆ IDE-guided workflow
    Pisa ★★★☆☆ Two DSLs to learn, but a good tutorial
    AIUP ★★★☆☆ A structured process, but many artifacts
    BMad ★★★☆☆ Many skills/commands
    JHipster ★★☆☆☆ JDL and many options, a steep curve

    Pisa's trade-off: More powerful, but requires learning DML and ADL.

    10. Community / maturity¶

    Tool Rating Reason
    JHipster ★★★★★ 10+ years, huge community, enterprise use
    Spec Kit ★★★★★ GitHub/Microsoft, a massive push since Sep 2025
    Kiro ★★★★☆ AWS backing, active development
    OpenSpec ★★★★☆ YC-backed, ThoughtWorks Radar
    BMad ★★★☆☆ Active open source community
    AIUP ★★☆☆☆ New, small community
    Pisa ★☆☆☆☆ A thesis prototype, a one-person project

    Pisa's reality: A research prototype, not designed for broad adoption.

    Pros and cons at a glance¶

    Pisa¶

    Pros Cons
    ✅ 100% deterministic — same input = same output ❌ Only two target platforms (Spring, Hono)
    ✅ Schema-validated specs — hallucination prevented structurally ❌ Steep learning curve (two DSLs)
    ✅ Full IDE integration with LSP ❌ No community (a single project)
    ✅ Tests as first-class output, including use case tests ❌ Not agent-agnostic
    ✅ UI from Salt mockups ❌ Limited platform variety
    ✅ Open source

    GitHub Spec Kit¶

    Pros Cons
    ✅ Agent-agnostic (30+ agents) ❌ Not deterministic (LLM variance)
    ✅ Huge community, Microsoft backing ❌ No schema validation against a domain model
    ✅ Easy start ❌ No guaranteed test/UI generation
    ✅ Flexible for any platform ❌ Specs are prose, not typed

    OpenSpec¶

    Pros Cons
    ✅ Minimalist, quick to learn ❌ Not deterministic
    ✅ Agent-agnostic ❌ No code generation (planning only)
    ✅ YC-backed, active development ❌ No UI/test focus
    ✅ Good for brownfield ❌ Less structure

    AIUP¶

    Pros Cons
    ✅ Use cases at the center ❌ Small community
    ✅ Traceability (test ↔ requirement) ❌ Focus on Java/Vaadin
    ✅ IDE navigator plugin ❌ Heavily Claude Code oriented
    ✅ Structured process

    Kiro (AWS)¶

    Pros Cons
    ✅ Complete IDE with SDD built in ❌ Proprietary (not open source)
    ✅ AWS ecosystem integration ❌ Vendor lock-in
    ✅ EARS notation for requirements ❌ Not agent-agnostic
    ✅ End-to-end workflow

    BMad¶

    Pros Cons
    ✅ Agile philosophy ❌ Many skills to learn
    ✅ Open source ❌ Not deterministic
    ✅ Agent-flexible ❌ Less structured than the others

    JHipster¶

    Pros Cons
    ✅ 100% deterministic ❌ Steep learning curve
    ✅ Huge community, 10+ years ❌ No agent/LLM support
    ✅ Enterprise-ready ❌ Monolithic (all or nothing)
    ✅ Complete full-stack apps ❌ Less flexible

                           │
                      Kiro ┤

                           │

                 Generator-driven (deterministic)

    Pisa positions itself in the quadrant "high structure + deterministic" — like JHipster, but with LLM support for the proposal phase. The other SDD tools (Spec Kit, OpenSpec, BMad) are more flexible, but less deterministic.

    Conclusion¶

    Pisa is unique in the combination of: 1. a typed DSL (not just Markdown specs) 2. deterministic generation (no LLM code) 3. schema validation (specs against the domain model) 4. test generation (including use case browser tests)

    The trade-off: less flexible and a smaller community than the agent-based approaches.

    Recommendation by use case: - Brownfield, quick start: OpenSpec or Spec Kit - Enterprise, established: JHipster - AWS ecosystem: Kiro - Use-case-centered: AIUP - Deterministic + specs + tests: Pisa
