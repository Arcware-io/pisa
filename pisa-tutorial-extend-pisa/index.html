    Tutorial: Pisa selbst um ein Feature erweitern (pisa extend)¶

    Du erweiterst Pisa, nicht ein erzeugtes Projekt. Der Ablauf folgt in vier Phasen dem von GitHub Spec Kit (specify, plan, implement, converge): erst eine Spec, dann ein Plan, dann die Umsetzung, am Ende eine Prüfung, ob alles stimmt. Pisa selbst schreibt dabei nur die Spec (mit einem Sprachmodell) und den Plan; den Code schreibt ein Coding-Agent (Claude Code, pi oder du), und Pisa prüft das Ergebnis.

    Stand: pisa 0.13.0 plus pisa extend. Befehle im Detail: User Guide und pisa extend --help. Dauer: eine bis zwei Stunden für ein kleines Feature. Dieses Tutorial gehört nicht zu pisa init und wird nicht mit pisa play abgespielt (der Coding-Agent ist nicht scriptbar).

    Das Beispiel ist ein erfundenes, kleines Feature: die Grösse des Verbindungspools (Hikari) in der Architektur-Beschreibung einstellen können. Ob es das in Pisa schon gibt, siehst du im Schritt 2; ersetze es sonst durch deinen eigenen Wunsch.

    0. Voraussetzungen¶

    Was Prüfen
    Ein Checkout von Pisa der Ordner AISE/ mit projects/pisa und projects/dml-lang; pisa extend läuft nicht im installierten Binary. Im Checkout: cd AISE/projects/pisa && bun install
    Bun bun --version. Pisa wird im Checkout mit bun run src/cli.ts … gestartet (unten kurz pisa geschrieben: alias pisa="bun run $PWD/src/cli.ts")
    Node.js und npm für dml-lang (npm run bundle)
    LLM-Zugang für pi nur für Schritt 2 (--specify) nötig
    Ein Coding-Agent für Schritt 5; hier Claude Code, geht auch von Hand

    Alles läuft im Checkout: pisa extend sucht von deinem Ordner aufwärts den Ordner AISE/ (oder du gibst --root <AISE-Ordner> an).

    1. Die Regeln lesen (Constitution)¶

    cat AISE/specs/constitution.md

    Du solltest sehen: die Regeln, die für jedes Feature gelten: Spec zuerst, deterministisch, Tests als Orakel, Bestehendes bleibt byte-gleich, Dokumentation im selben Schritt, kein git commit durch den Agenten. Die Datei ist der Spec-Kit-Schritt constitution; das Sprachmodell in Schritt 2 und der Coding-Agent in Schritt 5 lesen sie. Ändere sie, wenn sich eine Regel ändert, nicht pro Feature.

    2. Das Feature beschreiben (--specify)¶

    pisa extend --specify "Die Grösse des Hikari-Verbindungspools soll in der .adl einstellbar sein, im Block der Datenbank. Nur Spring. Standard bleibt wie bisher."

    Du solltest sehen: das Sprachmodell antwortet über ein geprüftes Werkzeug (submit_feature_spec). Lehnt Pisa die Antwort ab (unbekannte Schicht, keine Akzeptanzzeile, Schicht docs fehlt), bekommt das Modell die Gründe zurück; nach drei Versuchen bricht Pisa ab. Dann:

    Feature spec written:
  AISE/specs/features/001-hikari-pool-groesse/spec.md

    Die Datei hat feste Abschnitte:

    Abschnitt Inhalt
    Zweck wozu und warum
    Beispiel wie es in der .adl aussähe, z. B. container store : database { engine postgresql pool 10 }
    Akzeptanz Tabelle «Eingabe → Erwartet», jede Zeile muss ein Test prüfen können
    Regeln was der Validator als Fehler meldet, was nur als Warnung (z. B. pool unter 1)
    Schichten die betroffenen Schichten der Checkliste: dml-lang, dml-lang-tests, pisa-plan, pisa-llm, pisa-profiles, pisa-cli, pisa-tests, docs
    Offen Fragen, die der Wunsch nicht beantwortet (das Modell soll nicht raten)

    Lies die Spec und korrigiere sie von Hand, bevor du weitermachst: das ist die eigentliche Entscheidung. Ob die Schichten stimmen, siehst du an der Liste: ein neues Schlüsselwort in der .adl braucht dml-lang; soll das Modell bei propose-architecture den Wert wählen können, kommt pisa-llm dazu; ändert sich eine erzeugte Datei (application.yml), pisa-profiles.

    3. Den Plan erzeugen (--plan)¶

    pisa extend --plan --state

    Du solltest sehen: Plan written: …/001-hikari-pool-groesse/plan.md (N tasks) und Tasks appended to …/.agent-state.md. Ohne Modell: Pisa nimmt die Schichten aus der Spec und schreibt die Aufgaben der Checkliste, je mit den Dateien, die dran sind:

    ## dml-lang: Grammatik, Validator, Formatter

- [ ] [dml-lang] Grammatik erweitern (`projects/dml-lang/src/adl.langium`)
- [ ] [dml-lang] Validator: Fehler und Warnungen (`projects/dml-lang/src/adl-validator.ts`)
…

    --state hängt die Aufgaben an AISE/.agent-state.md an (Regel aus AGENTS.md: jede Aktion steht vorher dort). Ein vorhandener Plan wird nie überschrieben (seine Haken gingen verloren); willst du neu planen, lösche plan.md.

    Auf dem Board (AGENTS.md): ein Issue für das Feature, die Aufgaben als Unter-Issues mit Aufwand.

    4. Den Auftrag ansehen (--implement)¶

    pisa extend --implement

    Du solltest sehen: den Auftrag für den Coding-Agenten: die Regeln, die Spec und den Plan in einem Text. Pisa schreibt hier keinen Code (ein Modell mit Schreibzugriff auf die Pfade des Plans ist nicht gebaut, Pisa#97). Das ist die Schnittstelle zu deinem Agenten.

    5. Umsetzen¶

    Gib dem Coding-Agenten den Auftrag, z. B. in Claude Code im Ordner AISE/:

    Setze das Feature 001-hikari-pool-groesse um. Lies AISE/specs/constitution.md, die spec.md und die plan.md in
AISE/specs/features/001-hikari-pool-groesse/. Arbeite die Aufgaben der Reihe nach ab und hake sie in plan.md ab.

    Die Reihenfolge der Schichten ist die der Checkliste:

    1. dml-lang: Grammatik (adl.langium), Validator, Formatter, Fixtures und Tests, Beispiel; dann npm run bundle im Ordner dml-lang (erzeugt den Parser und den Bundle für die Plugins); in projects/pisa danach bun install.
    2. pisa-plan: Wert im Plan und in adl.ts/adl-text.ts lesen und schreiben.
    3. pisa-profiles: die Vorlage (application.yml.njk) schreibt den Wert, nur wenn er gesetzt ist.
    4. Tests: Fixture-Tests für die Sprache, Vorlagen-Tests für die Ausgabe.
    5. docs: User Guide (Befehle, Optionen, «Noch nicht möglich», Version), Pisa-README, findings.md, Plan, State.

    Bleibt eine Zeile unklar, wiegt die Constitution mehr als die Spec: ohne den neuen Wert bleibt alles byte-gleich (der Schnappschuss test/profiles/__snapshots__/spring-boot.test.ts.snap darf sich nicht ändern).

    6. Prüfen (--check)¶

    pisa extend --check

    Du solltest sehen (dauert, die Tests laufen mit; die Zahlen sind beispielhaft):

    ok   spec.md - 5 layer(s)
ok   tasks - 17 done, 0 open
ok   docs - user guide and plan changed
ok   pisa: bun test - 962 pass | 36 skip | 0 fail
ok   pisa: tsc
ok   dml-lang: bun test - …

Converged: 001-hikari-pool-groesse

    Nicht fertig, wenn etwas fehlt: Pisa listet die Lücken (FAIL tasks - 3 open, FAIL docs - not changed: doc/plan/project.md) und endet mit Exit 1. Beheben, --check nochmal. Schneller Zwischenstand ohne die Tests: pisa extend --check --skip-tests.

    --check prüft, was sich prüfen lässt (Tests, Typen, Aufgaben, Dokumente). Dass die Spec richtig war, prüft es nicht; das ist deine Entscheidung in Schritt 2.

    7. Abschliessen¶

    • git status ansehen, committen machst du selbst (der Agent tut es nie).
    • Auf dem Board die Issues auf Done, im Plan (doc/plan/project.md) die Aufgabe nachführen.
    • Ein weiteres Feature: Schritt 2 mit einem neuen Wunsch; die Nummer läuft weiter (002-…). Mit --feature <NNN> wählst du ein älteres Feature, sonst gilt das neueste.

    Wie das zu Spec Kit passt¶

    Spec Kit pisa extend Unterschied
    constitution AISE/specs/constitution.md (Schritt 1) gleiche Idee; unsere Regeln enthalten Determinismus und Byte-Gleichheit
    specify, clarify --specify (Schritt 2) das Modell darf nur über ein Werkzeug antworten, das die Spec prüft (feste Abschnitte, bekannte Schichten)
    plan, tasks --plan (Schritt 3) ohne Modell, aus einer festen Checkliste; zusammengelegt
    implement --implement + Coding-Agent (Schritte 4 und 5) Pisa druckt den Auftrag, schreibt keinen Code
    converge --check (Schritt 6) deterministisch: Tests, Typen, Haken, Dokumente

    Wenn etwas nicht klappt¶

    Meldung Ursache
    pisa extend works in a checkout of Pisa … nicht im Checkout; in AISE/ wechseln oder --root <AISE-Ordner>
    There is no feature yet Schritt 2 fehlt
    … exists already (its ticks would be lost) plan.md gibt es; löschen, wenn du neu planen willst
    Only one phase at a time zwei Phasen-Schalter in einem Aufruf
    Unknown layer(s) in spec.md beim Korrigieren eine Schicht erfunden; erlaubt sind die acht aus Schritt 2
    Feature spec ended without an accepted spec das Modell hat nach drei Versuchen aufgegeben; Wunsch genauer formulieren und wiederholen
